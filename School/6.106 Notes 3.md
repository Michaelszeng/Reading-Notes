Statistics
- Measure the min. (b.c. the min. is closest to performance with no noise)
- When comparing ratios of runtimes, use the geometric mean (this way, mean of $\frac{A}{B}$ is $1/$mean of $\frac{B}{A}$)
Methods for timing
- `/usr/bin/time`: prepend before calling your binary; measures `real`, `user`, `sys` time
- `clock_gettime(CLOCK_MONOTONIC, ...)`
	- runs in ~80ns
- `rdtsc()`: measures CPU cycles since boot
	- Weird artifacts; may move backwards if switching processors, since different processors may have different answers to `rdtsc()`
	- Not all cycles take the same amount of time (i.e. DVFS, Turbo Boost, AVX instructions)
	- runs in ~32ns
- `lbpfm4`: hardware counters, count number of event occurrences per process
	- What `perf` uses
Quiescing the system during testing
- Kill all jobs
- Disconnect from network
- Disconnect mouse (this triggers interrupts)
- Don't run on core 0 (which handles a lot of interrupts)
- Use Linux CPU frequency governor
- Use `taskset` to pin thread to a given core; prevent jumping to other cores (which wipes cache and messes up timers, for example)
Simple techniques
- Don't measure single runs at all; run 100 times, then divide by 100
- Start measuring after the code has warmed up (warm up caches, warm up branch predictors)

## Determinism and Locking
- *Determinism*: each memory location sees same sequence of updates every run
- *Critical Section*: piece of code that should be atomic
	- Surround w/ `lock` and `unlock`
- If 2 parallel threads access same memory location (and one writes) (i.e. a *Data Race*), program is non-deterministic
	- Locks can remove the Data Race and make the program safe, but using locks inherently implies the above $\rightarrow$ non-determinism
- Locks affect parallelism (the length of the critical section must be run serially)
Types of Mutexes:
- *Yielding* vs *Spinning*: yield control to OS while waiting vs wasting processor cycles while waiting
	- Spinning: Fastest -- gets lock as soon as its free
	- Yielding: More efficient, but more overhead from context switching; doesn't acquire lock as fast
- *Re-entrant*: allows thread that is already holding a lock to acquire it again (vs deadlocking if the same thread tries to acquire a lock multiple times)
- *Unfair* vs *Fair*: Unfair = lets any blocked thread go next; Fair = lets the thread that's been waiting the longest go next (keeps FIFO queue of waiting threads)
Basic Spin Lock implementation:
	<center><img src="School Supplements/6.106_mutex_spin_mutex.png" alt="" style="width:400px; margin-top: 10px"/></center>
- Note: `xchg` is atomic hardware op to acquire mutex
Competitive Mutex:
- Balance btwn *Spinning* & *Yielding*
- Spin for a while, (and if the mutex still isn't available) then yield
- How long to spin?
	- Strategy: wait as long as a context switch caused by a yield
	- Results in 2x optimal waiting time
		- If mutex released while spinning $\implies$ optimal waiting then (no context switch time needed)
		- If mutex released after yield $\implies$ 2x optimal (1x context switch needed, but at least 1x context switch waiting time was already needed)
Cache Contention
- Problem: if many threads waiting on the same lock (assuming spinning mutexes), once that lock is free, they all jump on it, all attempt to write `xchg` at the same time into the bus
	- This flooding of the bus is slow; requires a *quiescence time* for the bus arbitrator to resolve conflicts + pick one winner + then invalidate the cache line containing the lock in the caches of all non-winner processors 
- Solution: (Exponential) Random Backoff mutex
Deadlock
- Conditions for Deadlock
	- Mutual Exclusion (using locks)
	- Non-preemption (neither gives up until lock acquired)
	- Circular waiting (A waits for B, B waits for A)
- Theorem: We can guarantee no deadlock if:
	- For some arbitrary order of all mutexes: $L_1 < L_2 < \dots < L_n$
	- Whenever a thread holds $L_i$, it can only attempt to acquire another mutex $L_j$ if $L_i < L_j$
	- Proof: 
		- The thread holding $L_{max}$ cannot be waiting on any mutex; so it will finish, then anything waiting on $L_{max}$ will finish, etc.
- Deadlocks can still occur w/only one mutex/lock if there is parallelism, i.e.:
		<center><img src="School Supplements/6.106_mutex_single_lock_deadlock.png" alt="" style="width:200px; margin-top: 10px"/></center>
	- Solution: only use a lock within a `cilk_scope`
Convoying
- When multiple threads try to acquire lock on the same object; they must basically wait in line
- KEY IDEA: Often better to use non-blocking `try_lock()` instead of blocking `lock()`
	- If `try_lock()` fails, then go do something else
- Example: random work-stealing
	- With normal `lock()`: At program start, thread 1 starts with all the work; all other threads randomly try to steal work from each other, but all converge to locking onto thread 1 (since it has all the work). All threads wait in line.
	- Instead, use `try_lock()`: 
		- If a thread tries to steal from thread 1, but it's busy, doesn't get stuck on it; continues trying to steal from other processors
		- Eventually, the work spreads out, and the threads steal from each other instead of all from thread 1

## Cache-Efficient Algorithms
Cache Hardware
- Individual processors have their own L1D (data) + L1I (instruction), L2 caches
- L3 (LLC -- "last-level cache") often shared across processors
- ~3000 flops per DRAM access
- Cycles:
	- DRAM: 100-250 cycles, many GiB
	- L3: 50-70 cycles, 1 MiB
	- L2: 10-20 cycles, 1 MiB
	- L1: 4-5 cycles, 32 KiB
Review
- Terminology: 
	- "Cache block" vs "Cache line":
		- *"Cache block"* refers to the actual data that fits in a cache line
		- *"Cache line"* refers to the place in the cache hardware for a cache block to be stored
	- *Offset*: used to index to a byte within a cache line
	- *Tag*: used as a unique identifier for a cache block during retrieval. 
- Cache Associativity
	- Fully Associative Cache: 
		- Each line in memory can reside in any line of cache
			- When retrieving data from cache, every way in every set in cache must be searched
					<center><img src="School Supplements/6.106_cache_fully_associative.png" alt="" style="width:500px; margin-top: 10px"/></center>
		- Require $\log B$ bits to index within a cache line; remaining bits of the address as used as the tag
						<center><img src="School Supplements/6.106_cache_fully_associative_tag_offset.png" alt="" style="width:300px; margin-top: 10px"/></center>
		- Processors have hardware to check tag-match ("content-addressable lookup") for all ways of cache at the same time
		- Ideal for temporal locality -- no random cache conflicts; data only gets evicted based on temporal locality
	- Direct-Mapped Cache: 
		- Each line in memory maps to exactly one line/*set* in cache
			- During data retrieval, only need to check that one line/*set*
							<center><img src="School Supplements/6.106_cache_direct_mapped.png" alt="" style="width:500px; margin-top: 10px"/></center>
		- $\log B$ bits to index within a cache line; $\log(M/B)$ to index into the right line/*set*; remaining bits of the address as used as the tag 
					<center><img src="School Supplements/6.106_cache_direct_mapped_tag_set_offset.png" alt="" style="width:300px; margin-top: 10px"/></center>
		- Ideal for spatial locality; if program accesses many variables adjacent in memory (which has same tag but different set) gets mapped to different cache sets; can all exist in cache at the same time
	- $k$-way Set-Associative Cache:
		- Each line in memory can reside in one of $k$ cache *ways* in that particular cache *set*
			- During data retrieval, all $k$ ways of the corresponding set must be searched to find matching tag
		- 2 different visualizations:
				<center><img src="School Supplements/6.106_cache_sets_ways.png" alt="" style="width:400px; margin-top: 10px"/> <img src="School Supplements/6.106_cache_set_associative.png" alt="" style="width:500px; margin-top: 10px"/></center>
		- $\log B$ bits to index within a cache line; $\log(M/kB)$ to index into the right line/*set*; remaining bits of the address as used as the tag
				<center><img src="School Supplements/6.106_cache_set_associative_tag_set_offset.png" alt="" style="width:300px; margin-top: 10px"/></center>
		- A compromise between Direct-Mapped cache (effectively a $M/B$-set 1-way Set-Associative Cache) & Fully Associative Cache (effectively a $M/B$-way 1-set Set-Associative Cache)
Taxonomy of Cache Misses
- *Cold miss*: block has never been accessed before. Unavoidable
- *Capacity miss*: block has been evicted simply bc cache is not large enough (and would have been evicted even if you had a fully associative cache)
- *Conflict miss*: block has been evicted bc of conflicts w/other blocks that map to the same set in the cache (but would still be in cache if you had a fully associative cache)
	- This is why you want $k$ in your set-associative cache to be reasonably large -- to avoid conflicts within sets
- *Sharing miss*: another processor has exclusive access to the cache block
	- *True-Sharing miss*: 2 processors access same data on the cache block
	- *False-Sharing miss*: 2 processors access different data on the same cache block
Cache Analysis & Ideal Cache Model
- Analysis metrics:
	- Work $T$
	- Cache misses $Q$
- Ideal Cache Model
	- Fully associative cache w/optimal, omniscient eviction/replacement strategy (therefore no conflict misses)
	- Theorem: if algorithm incurs $Q$ cache misses on ideal cache of size $M$, it incurs $\le 2Q$ cache misses on a real-life LRU fully-associative cache of size $2M$.
- ***Segment Caching Lemma***
	- Suppose program reads $r$ data segments, i'th segment consists of $s_i$ bytes, $N$ = total size of all data segments, $B$ = cache block size (i.e. 64 bytes)
		- $N/r$, average size of data segment
	- Suppose:
		- $\sum_{i=1}^r s_i = N < M/3$  (program reads < 1/3 of entire cache)
		- $N/r \ge B$ (average segment is longer than $B$, a single cache line)
	- number of misses to read all data is $\le 3N/B$
		- 3x optimal (since at least $N/B$ cache misses are necessary due to cold misses)
	- Proof:
		- $\sum_{i=1}^r (s_i / B + 2) = N/B + 2r \le N/B + 2(N/B) = 3N/B$
		- Intuition: Each read of $s_i$ data covers at most $s_i / B$ cache lines, $+2$ if it happens to overlap w other cache blocks at the edges of $s_i$. Worst case is that all $s_i / B + 2$ blocks result in misses
			<center><img src="School Supplements/6.106_cache_segment_caching_lemma.png" alt="" style="width:250px; margin-top: 10px"/></center>
- Short Caches vs Tall Caches
	- *Tall cache*: if $B^2 < cM$ for some small constant $c\le1$.
	- Tall caches are better:
		- i.e. consider trying to access a $n \times n$ submatrix (in a larger matrix that is stored in row-major order) (where $B \gg n$). 
		- To access one row of the submatrix, you have to load one cache line, which also consists of data surrounding the row of the submatrix
			- This is wasted cache space (assuming we only care about the submatrix)
		- Smaller $B$ gives more flexibility to load/store just the data you need
	- ***Submatrix Caching Lemma***
		- $n \times n$ submatrix $A$ read into tall cache ($B^2 < cM$), $c < \frac{1}{3}$, $cM \le n^2 < \frac{M}{3}$.
		- Then, $A$ fits into cache, number of misses to read all of $A$'s elements $\le \frac{3n^2}{B}$.
		- Proof: apply segment caching lemma with $r$ reads of $s_i = n$.
- Example:
	- Tiling mat-mul.
		- Assuming each submatrix tile of size $s$ fits in cache with $s^2 < \frac{M}{3}$
		- Then, by Submatrix Caching Lemma, each tile incurs $\le \frac{3s^2}{B}$ cache misses
		- $(n/s)^3$ accesses to tiles in the matrix $\rightarrow \Theta((n/s)^3 * s^2/B) = \Theta(n^3/sB) = \Theta(n^3/BM^{1/2})$ cache misses
	- Divide & Conquer Recursive mat-mul.
			<center><img src="School Supplements/6.106_example_divide_and_conquer_mat_mul.png" alt="" style="width:400px; margin-top: 10px"/></center>	
		- Recurrence Relation: $Q(n) = 8Q(n/2) + \Theta(1)$
			- Base case: $\Theta(n^2/B)$ by Submatrix Caching Lemma (assuming $n^2 < \frac{M}{3}$ in the base case)
Cache-Oblivious Algorithms
- No knowledge or parameter-tuning based on cache sizes
- Implicitly auto-tuned and handles multi-level caches automatically
Cache Analysis & Parallelism
- Theorem: $Q_p = Q_1 + O(S_p M/B)$
	- $S_p$ = # of steals (number of times work is transitioned between processors)
	- i.e. cache misses w/$P$ processors = cache misses w/$1$ processor + work-stealing overhead
	- Work-stealing overhead: worst case, all of the $M/B$ lines of cache are cold --> $M/B$ misses per steal, with $S_p$ steals
	- Basically: there is no known good bound/algorithm for cache misses during work-stealing.
- IN PRACTICE: minimizing cache misses in serial projection --> minimizes the in parallel execution too
General Analysis Strategy:
- Always check conditions for *Segment/Submatrix Caching Lemma*
- Otherwise, just logic? Think about order of accesses + which will get wiped from cache
### Cache Oblivious Algorithms
EXAMPLE: 
- If $Q$ is $\Theta(c/B)$ for some $c$, implies spatial locality?
- If $Q$ is $\Theta(c/M)$ for some $c$, implies temporal locality?
- Example:
	- Define "Trapezoid" ("zoid"): 2 parallel bases (parallel to x-axis), legs of slope either $1$, $-1$, or $\infty$
	- Non-base cases:
		- If width >= 2 $*$ height: split zoid down the middle
			- PICTURE
			- Compute the 2 resulting zoids recursively (right zoid must be computed *after* left zoid (depends on pink points))
			- PICTURE
		- Else (width < 2 $*$ height): split zoid using cut through time-axis
			- Process 2 resulting zoids recursively (top zoid computed *after* bottom zoid)
	- Base case: if height of zoid $== 1$
	- Analysis: 
		- Recursive tree:
				- PICTURE
		- Each leaf trapezoid has $h = \Theta(w)$
		- Bottom of leaf zoid fits in cache, i.e. $w = \Theta(M)$
		- Leaf incurs $\Theta(w / B)$ cache misses
		- $\Theta(NT/hw) = \Theta(NT/w^2)$ leaves (and same number of internal nodes since the recursive tree is a binary tree)
		- Work $T_1$: $\Theta(1)$ work per internal node, $\Theta(w^2)$ work per leaf --> $\Theta(1) * \Theta(NT/w^2) + \Theta(w^2) * \Theta(NT/w^2) = \Theta(NT)$
		- Cache Misses $Q$: $\Theta(1)$ work (and therefore cache misses) per internal node, $\Theta(w/B)$ cache misses per leaf --> $\Theta(1) * \Theta(NT/w^2) + \Theta(w/B) * \Theta(NT/w^2) = \Theta(NT/Bw) = \Theta(NT/BM)$
			- Takes advantage of both spatial + temporal locality
	- Parallel Cache Oblivious Algorithms
		- Parallel Loops algorithm: bottlenecked by DRAM reading bandwidth saturation
		- Parallel Cache Oblivious Algorithm: relies more on cache and less on DRAM reading --> does not suffer from the same DRAM reading bandwith bottleneck
		- How to detect DRAM reading bandwidth saturation:
			- Compare runtime with one instance vs runtime when you spin $P$ instances (on a quiesced system) at the same time
			- If $P$ instances --> major slowdown, most likely competing for DRAM reading bandwidth
			- Assumes you have enough memory for $P$ instances
		- NOTE: cache efficiency tends to matter more for parallel programs where DRAM reading bandwidth is more likely to be a bottleneck?
	- NOTE: cache oblivious algorithms benefits diminish as dimension increases

## Storage Allocation
What is storage allocation?
- Algorithms for converting user's `malloc` request to actual pages/blocks in memory. Where do you put them? How do you manage multiple threads accessing same memory at same time?
Recap: Virtual Memory vs Physical Memory vs Disk
- Actual data lives in either physical memory or disk
- Virtual memory just abstraction of physical memory so each process sees own private address space 
- Disk used for long-term storage
- Memory is divided into pages (which applies to virtual + physical + disk)
	- Page table handles translation of virtual page address to physical page address
	- Page fault: when physical page doesn't exist in physical memory, must retrieve page from disk
		-  *Disk Thrashing*: i.e. reads page A, evacuates page B, then needs to read page B, evacuates page A, repeat
	- OS can reclaim physical pages: writes page to disk; frees page from physical memory, unmap page in page table
- Address Translation: 
			<center><img src="School Supplements/6.106_address_translation.png" alt="" style="width:500px; margin-top: 10px"/></center>
	- virtual page # used as idx into page table, maps to frame # (i.e. physical page #)
	- offset in virtual address is copied directly to physical address; determines where in page to index to
	- Hierarchy of page tables: 
			<center><img src="School Supplements/6.106_hierarchy_of_page_tables.png" alt="" style="width:500px; margin-top: 10px"/></center>
		- 48-bit virtual address gets split into 9-bit segments; each segment maps to the correct next-level table
			- Each mini-table has $2^9 = 512$ entries
		- There are also different page sizes (4 KB, 2 MB, 1 GB pages) -- multiples of 512 of each other
			- Larger pages --> less TLB + page table overhead (if you use large contiguous sections of memory)
		- To access a larger page size, simply early-exit in the hierarchical page table; the remaining bits that are not used to index into page tables become offset bits
			- 4 KB pages have 12-bit offset
			- 2 MB pages have 21-bit offset
			- 1 GB pages have 30-bit offset
	- TLB: cache recent page-table lookups
- Addressing in Caches
	- Recall (in a standard 8-way Set Associative Cache):
		- Caches are shared across threads; use physical addresses for their "tags".
		- Caches are organized into 64-sets of 8 ways
				<center><img src="School Supplements/6.106_cache_sets_ways.png" alt="" style="width:400px; margin-top: 10px"/></center>
			- Each way represents 1 cache line
			- A given address maps deterministically to one cache set and a unique tag, but can be placed in any way (based on temporal locality?)
	- For a thread (that uses virtual memory) to access cache (which uses physical memory):
		1. Map virtual memory to physical memory to get the tag
		2. In parallel, use the offset bits (which are shared between the virtual and physical addresses) to find the right set + byte offset
			- For a 12-bit offset, first 6-bits index into the right cache set; last 6-bits index into the right byte in the 64-byte cache line
		3. Use the set + tag to find the right way, and use the byte index to find the right byte
		- This parallelizes some of the work of cache accesses (so we don't wait too long for the virtual --> physical address translation)
### Stack Allocation
- alloc/free takes $O(1)$
- Must alloc/free according to *Stack Discipline*: LIPO (last in first out)
### Heap Allocation
Key functions:
- `void* malloc(size_t s)`, `void* free(void* p)`
- `mmap`: allocate a new address space/virtual memory space
	1. allocate a new virtual page (but not yet mapped anywhere in physical memory yet)
	2. at first access to that page, you get a page fault
	3. then, invoke OS to allocate physical memory for the new page
- `malloc` vs `mmap`:
	- `mmap` is heavy-weight kernel function (~1M cycles)
	- `malloc` is light-weight user-space function; calls `mmap` under the hood only if you actually need a new page allocated
Key Properties of Allocators:
- *Allocation Speed*: care about allocating small blocks fast (big blocks get amortized over lots of reads/writes)
- *User footprint*: $M$ = max # bytes in use by user program
- *Allocator footprint*: $H$ = max # bytes provided to allocator by OS
- *Fragmentation*: $F = H/M$: wasted space (ratio of allocator allocated / user asked for) 
	- Multiple contributing factors:
		- *Space overhead*: space used by allocator for book-keeping
		- *Internal Fragmentation*: wasted allocation due to allocating lager blocks than user requests (i.e. if you can only allocate powers of 2)
		- *External Fragmentation*: wasted space due to non-contiguous allocations (i.e. gaps in memory space) between allocations
		- *Blowup*: overhead of parallel allocator
- *Space utilization*: $M/H$: how much of the allocator allocated space is used by user program
Headers:
- Stored right in front of actual data allocation during `malloc()`
- Contain metadata (most importantly, *size* of the allocation)
- During `free((void*) p)`, the header is read first to determine the size of the block to free

#### Serial Allocators
- Goal of storage allocators: minimize used virtual memory
	- minimize fragmentation, maximize space utilization
- Bitmap Allocator
	- Pre-determined block sizes; use bitmap to indicate whether each block is free or not
	- Choose lowest-bit free block to allocate
	- Pros:
		- can have small block size
		- some bit-tricks that help
		- can be made hierarchical
		- spatial locality
- *Free List*
	- Pre-determined block sizes; each block contains pointer to next free block; maintain pointers during alloc/free (basically just a single-linked list)
			<center><img src="School Supplements/6.106_storage_allocator_free_list.png" alt="" style="width:400px; margin-top: 10px"/></center>
		- During `malloc`: 
			- If free list NOT empty: alloc the head block and then delete the head from the linked list (`block = head`, `head = block->next`)
			- If free list is empty:      alloc new block from heap and return that block
		- During `free`: Freed blocks get pre-pended as a new head of the linked list (`block->next = head`, `head = block`)
	- In practice: all the `next` ptrs of the free list are stored in the free blocks -- doesn't require extra space --> low *space overhead*
	- Pros:
		- alloc/free in $O(1)$
		- temporal locality (tends to re-alloc same blocks as have been previously alloc'ed/freed)
	- Cons:
		- spatial locality (read blocks/pages from all over the place) --> disk thrashing
- Binned Free Lists
		<center><img src="School Supplements/6.106_storage_allocator_binned_free_list.png" alt="" style="width:400px; margin-top: 10px"/></center>
	- Use a *free list* for every bin
	- Alloc block in the smallest free bin that can store the desired size
		- If the smallest available block is much larger than the user needs, split it and move those (now smaller) blocks to the correct bin
		- If you run out of bigger blocks to allocate, ask OS to alloc more
	- Theorem: if user footprint is $M$, allocator footprint is $O(M \log M)$
	- *Coalescing*: splicing together adjacent small blocks into larger block
		- largely heuristic ("buddy system") -- no proven bounds/algorithms
		- major limitation: can only coalesce *adjacent* blocks, which in practice is still good (users often de-alloc contiguous batches of blocks)
	- Pros:
		- Same pros as Free List
		- Handle variable-length allocs
	- Cons:
		- Internal fragmentation (but a bounded amount)
#### Parallel Allocators
- i.e. multiple threads trying to alloc at the same time
- Global Heap Allocator (the simplest thing possible)
	- all threads share a single heap; accesses use mutex lock
	- 1x blowup (no blowup) -- only one allocator and 1 lock
	- slow (lock contention)
- Local Heaps Allocator
	- Each thread has separate local heap (no locking)
	- Fast (no synchronization)
	- Unbounded blowup -- is threads access shared memory, and one tries to alloc and another tries to free, how do you handle this?
- Local Ownership Allocator
	- Each alloc'ed object is assigned owner thread
	- Each thread still has own heap
	- If a different thread tries to free the memory than the alloc'ing thread, it hands responsibility back to the alloc'ing thread via synchronization
	- Blowup $\le P \times$ ($P$ = # processors)
	- Pros:
		- bounded blowup compared to Local Heaps Allocator
		- fast allocation and freeing of local objects (that live in a single thread)
	- Cons:
		- requires synchronization for memory that is accessed by multiple threads
- Hoard Allocator
	- 1 global heap, $P$ local heaps (one for each thread)
			<center><img src="School Supplements/6.106_storage_allocator_hoard_allocator.png" alt="" style="width:300px; margin-top: 10px"/></center>
	- Memory organized into superblocks of size $S$
	- Superblocks can be moved between local heaps and global heap
		- global heap acts like a shared memory-balancing pool
	- How allocation works:
		- If local heap has open superblocks, pick the fullest non-full superblock to alloc into (want to minimize the # of total superblocks to minimize internal fragmentation and avoid having to copy back and forth to global heap)
		- Elif global heap has open superblocks, alloc there
		- Else, ask OS for more local superblocks
	- How freeing works:
		- Move the superblock containing the to-be-dealloc'ed object back to heap $i$
		- Free the object
		- Check if heap $i$ has too much under-utilized memory/superblocks
			- Maintains invariant: $m_i \ge \min(h_i - 2S, \frac{h_i}{2})$ -- in use storage by thread $i$ $\ge$ half the allocated storage, and ensure $< 2S$ unused memory
			- If so: move a superblock back to the global heap
	- Pros:
		- Same as Local Heaps Allocator, but allows some degree of sharing memory between threads via global heap
		- Bounded Blowup ($H \le O(SP + M)$ -- total hoard allocator footprint proportional to program footprint + extra superblock for each processor)
		- No *False Sharing*:
			- 2 threads using two different blocks that get put on same cache line
				- if they both try to write at the same time, they fight for **M** (modify) access to that cache line and invalidate each others caches
			- Hoard allocator allows different threads' memory in different supreblocks --> never in same cache line

### Garbage Collection (GC)
- Automatically detects when to `free()`
- Built-into languages like Python, Java
- Can be hand-made
Terminology:
- *Roots*: objects accessible by the program
- *Live Objects*: reachable from root by following pointers
- *Dead Objects*: no longer accessible, can be recycled
How GC identifies pointers:
- Count pts pointing at each object. If it's 0, object is dead
- Problem: never collects dead cycles:
				<center><img src="School Supplements/6.106_garbage_collection_dead_cycle.png" alt="" style="width:400px; margin-top: 10px"/></center>
Mark and Sweep Garbage Collection
- Objects + Pointers = Nodes + edges directed graph
- Use BFS to find live objects (starting from each root variable; in this case, just $R$):
	<center><img src="School Supplements/6.106_garbage_collection_BFS_dead_cycle.png" alt="" style="width:400px; margin-top: 10px"/></center>
Stop and Copy Garbage Collection
- Split heap into 2 halves: "FROM" and "TO"
- During the program, simply accumulate objects contiguously in "FROM" space
	- Keep track of all live/dead objects but never `free()` anything
- Once "FROM" half is full:
	- copy all live objects into "TO" half of the heap
	- update all pointers
	- swap "FROM" and "TO"
	- "throw away" the old "FROM" space
- Pros:
	- after the copy is performed, no internal fragmentation
	- fast allocation (just contiguous in memory)
- Cons: 
	- memory inefficient; requires expensive copy operations once in a while
Generational Garbage Collection
- Observation: Most alloc'ed memory dies young
- Strategy:
	- Garbage collect "nursery" often
	- Garbage collect "old generation" rarely
- Otherwise, use the Stop and Copy Garbage Collector

## Staging/Specialization
*Staging*: splitting execution into multiple stages
- 1st stage takes some inputs + generates code
- 2nd stage runs the generate code on remaining inputs
*Specialization*: Tailoring program to *specific inputs known ahead of time* to allow more compiler optimization.
- i.e. what's often done in the 1st stage
*BuildIt* Library:
- `static_var<T>` for variables known in stage 1, evaluated during stage 1
	- constants
	- loop indices for loops we want evaluated + unrolled into straight-line code during stage 1

## Multicore
Cache Coherence
- Processors use shared memory
- Each processor has its own cache
- Problem 1: memory is slow; inefficient for multiple processes to read from shared memory. Instead, it's faster for processors to share their cache data among each other
	- GOAL: give the illusion of shared memory, but actually share data between processes' caches
- Problem 2: If process x writes data to shared memory, then the cached value of that data in other processors' caches will become out of date
MSI Protocol
- Each cache line given a state:
	- **M**: cache block modified; all other caches must invalidate this line
	- **S**: other caches may be sharing this block
	- **I**: cache block invalid
- Processors communicate via commands (i.e. *BusRd*, *BusWr*, etc.) on shared comms bus
- Example (4 caches/processors):
			<center><img src="School Supplements/6.106_msi_protocol.png" alt="" style="width:400px; margin-top: 10px"/></center>	
- Rules:
	- On read:
		- If processor cache already has variable in **S** or **M**: read it locally
		- Else: issue *BusRd* $\rightarrow$
			- If no other cache has the line in **M**: requester gets the line in **S**
			- Else: other cache writes back the variable, downgrades from **M** to **S**, then requester also gets the line in **S**
	- On write:
		- If processor cache already has variable in **M**: writes locally, stays in **M**
		- Else: claims exclusive ownership of cache line (all other processors must downgrade to **I**), then switch locally to **M**
- Whenever you modify a cache line, you have to *invalidate* that line in all other caches

### Bounds on Parallelism
Trace DAG
- Vertices are strands -- sequence of instructions not containing a spawn or sync
- Edges are call sequences (spawns, call, return, or continue)
	<center><img src="School Supplements/6.106_fib(4)_trace_DAG_with_code.png" alt="" style="width:475px; margin-top: 10px"/><img src="School Supplements/6.106_fib(4)_trace_DAG.png" alt="" style="width:475px; margin-top: 10px"/></center>
- If there is a directed path between 2 nodes, they are *logically series*; else, they are *logically parallel*
Parallelism as a unit of measure
- Define $T_p$ = execution time on $P$ processors
	- $T_1$ = total work (i.e. serial runtime)
		- NOTE: work of parallel alg. always (asymptotically) equal to work of its serial projection
		- <sup><sub>In the case of parallelizing `for` loops or parallelizing function calls (possibly recursive), the serial projection is identical to the serial version, so work is the same.</sub></sup>
		- <sup><sub>If parallel algorithm is more than serial algorithm with `cilk_for` instead of `for` and added `cilk_scope`/`cilk_spawn`s, then the serial projection is different from the original serial algorithm; work can increase.</sub></sup>
	- $T_\infty$ = *span* -- length of longest path from $s$ to $t$ in trace DAG (*critical path*)
		- You can't avoid running these traces serially due to serial dependencies
		- runtime is at least as long as the span
- *Speedup* = given # processors $P$, how much faster code will be
	- If $\frac{T_1}{T_P} = P$, *perfect linear speedup* (as opposed to sublinear or superlinear)
		- Almost impossible in practice due to overhead
- *Parallelism* = *maximum* speedup compared to serial code
	- = $\frac{T_1}{T_\infty}$   (work / span)
- *Amdahl's law*: if $\alpha$ frac. of application must be run serially, then speedup can be at most $\frac{1}{\alpha}$
	- Speedup $= T_1 / T_p$
		     $\le T_1 / (α T_1 + \frac{(1 - α) T_1}{P})$      (because $T_P \ge \alpha T_1 + \frac{(1-\alpha)T_1}{P}$)
		 - As $P$ $\rightarrow \infty$, Speedup = $\frac{1}{\alpha}$
- *Work Law*: $T_p \ge T_1 / P$
		- runtime on $P$ processors is at least the total work divided by number of processors
		- i.e. best case is dividing total work equally by all processors
- *Span Law*: $T_p \ge T_\infty$
	- You can't beat the *span*'s runtime
	- Speedup $\le \frac{T_1}{T_\infty} =$ *parallelism*
- Fundamental Compositions of Work/Span:
	- Series Compositions
				<center><img src="School Supplements/6.106_series_composition.png" alt="" style="width:250px; margin-top: 10px"/></center>	
		- $T_1(A \cup B) = T_1(A) + T_a(B)$ -- total work = sum of individual work
		- $T_\infty(A \cup B) = T_\infty(A) + T_\infty(B)$ -- total span = sum of individual span
	- Parallel Compositions
				<center><img src="School Supplements/6.106_parallel_composition.png" alt="" style="width:150px; margin-top: 10px"/></center>	
		- $T_1(A ∪ B) = T_1(A) + T_a(B)$
		- $T_\infty(A \cup B) = \max(T_\infty(A), T_\infty(B)$) -- total span = max of individual spans
	- Example: Fibonnaci
		- $T_1(n) = T_1(n-1) + T_1(n-2) + \Theta(1) = \Theta(c^n)$
		- $T_\infty(n) = \max \{ T_1(n-1), T_1(n-2)\} + \Theta(1) = T_1(n-1) + \Theta(1) = \Theta(n)$
		- Parallelism: $\Theta(c^n/n)$ = very high
			- Fibonnaci achieves near-perfect-linear-speedup if $n$ large (but it's still a ton of work)
- Example:
			<center><img src="School Supplements/6.106_example_trace_DAG.png" alt="" style="width:150px; margin-top: 10px"/></center>	
	- At least 3 strands are serial (out of 18) -- Amdahl's law states: <= 6x speedup
		<center><img src="School Supplements/6.106_example_trace_DAG_serial_traces.png" alt="" style="width:150px; margin-top: 10px"/></center>	
	- $T_1$ = total work (i.e. serial runtime) = 18 (18 nodes total)
	- $T_\infty$ = *span* -- length of longest path from $s$ to $t$ = 9:

	- Possible Parallelism:
		- Amdahl's Law: 18 / 3 = 6x speedup
		- Span Law: 18 / 9 = 2x speedup
- Span Law is usually the tightest; actually considers serial dependencies in computation
	- Amdahl's law good for general understanding (non-specific to a given program or known serial dependencies)
	- Both give valid upper bounds on speedup

### Scheduling Theory
Greedy Scheduling
- A strand is *ready* if all predecessors have executed
	- i.e. if Blue = executed, then Yellow = *ready*
		<center><img src="School Supplements/6.106_executed_vs_ready_trace_DAG.png" alt="" style="width:150px; margin-top: 10px"/></center>	
- Scheduler greedily puts any available strands onto every available processor
	- *Complete step*: If all processors are occupied; $P$ processors, $\ge P$ strands *ready*
	- *Incomplete step*: $<P$ strands *ready*, scheduler executes all of them, but some processors idle
	- KEY GOAL: minimize # incomplete steps
- Theorem: Any greedy scheduler achieves $T_p \le \frac{T_1}{P} + T_\infty$
	- Recall: Work law: $T_p \ge T_1 / P$
			Span law: $T_p \ge T_\infty$
	- Proof: # complete steps $\le \frac{T_1}{P}$; # incomplete steps $\le T_\infty$ (because, in every incomplete step, one strand on the critical path must run)
		- In the worst case, all complete steps hit strands not on the critical path; then you still need $T_\infty$ incomplete steps to finish the critical path 
	- **Sum of span and work law lower bounds is an upper bound on runtime of greedy scheduler**
	- This implies greedy scheduler is $\le2 \times$ optimal scheduler
	- If $\frac{T_1}{T_\infty} \gg P$  (i.e. parallelism much larger than # processors, parallel slackness very high), approaching perfect linear speedup
		- There's almost always extra tasks to be scheduled
- *Parallel Slackness*: $\frac{T_1}{T_\infty} / {P}$   (parallelism divided by # processors)
	- Describes how much more parallelism you have than processors
	- Want this to be like 10x or more
	- Then almost all steps are complete steps
Cilk's Randomized Work-stealing scheduler:
- Achieves $T_p = \frac{T_1}{P} + O(T_\infty)$ (approximately 1x $T_\infty$ empirically) -- achieves roughly the greedy bound in practice
- `Cilkscale` allows you to measure work ($T_1$) and span ($T_\infty$) so you can check if $\frac{T_1}{T_\infty} \gg P$ and if you can expect ~linear speedup

			- The serial code does $O(n^2)$ work; work is asymptotically equal regardless of parallel vs serial implementation

					- $O(n)$ leaf nodes, doing up to $O(n)$ work each -- equivalent to serial work
					- Each internal (non-leaf) node is constant work -- just spawning children/control flow
						- $n-1$ internal nodes total
					- Still $O(n^2)$ work total
		- Span $T_\infty$: $O(n + log ~n) = O(n)$
			- Longest path through the DAG highlighted in yellow -- proportional to height of DAG = $O(log ~n)$
			- The leaf node does $O(n)$ work
		- Parallelism: $\frac{T_1}{T_\infty} = \frac{O(n^2)}{O(n)} = O(n)$

			<center><img src="School Supplements/6.106_cilk_parallel_loop_example_single_loop.png" alt="" style="width:550px; margin-top: 10px"/></center>	
	- Work $T_1$: $O(n)$
	- Span $T_\infty$: $O(log ~n)$
	- Parallelism: $\frac{T_1}{T_\infty} = O(\frac{n}{log ~n})$
Coarsening the recursion
- Compiler does do automatically; OR: force compiler using `#pragma cilk grainsize G` (ALMOST ALWAYS A BAD IDEA)
	- Cilk runtime coarsens recursion to try to get parallel slackness ~8-10
- With $G$ coarsened recursion:
		<center><img src="School Supplements/6.106_cilk_parallel_loop_example_single_loop_trace_DAG.png" alt="" style="width:550px; margin-top: 10px"/></center>	
	- Trace DAG has $\frac{n}{G}$ leaves
	- Define: $S$ = time for control flow to run (i.e. to compute `mid`, call `cilk_spawn`, `return`, etc.)
	- Define: $I$ = time for loop body to run (i.e. `A[i] += B[i]`)
	- Work: $T_1 = n·I + (n/G ~–~ 1)·S$   ($n \cdot I$ is constant, useful work from performing loop body; $n / (G - 1) \cdot S$ is $S$ overhead/control-flow work over $n / (G-1)$ internal nodes)
		- NOTICE: Larger $G$ reduces total work (reduces $(n/G ~–~ 1)·S$, the control loop overhead)
	- Span: $T_\infty = G · I + \log(n/G)·S$   ($G \cdot I$ is work of the leaf node which is coarsened $G$x; $\log(n / G) \cdot S$ is $S$ work over $\log(n / G)$ depth of the DAG)
		- Highlighted yellow
		- NOTICE: Smaller $G$ reduces total span (less work per leaf node)
	- Parallelism: $\frac{T_1}{T_\infty} = \frac{n·I + (n/G ~–~ 1)·S}{G · I + \log(n/G)·S}$
	- HOW TO PICK $G$:
		- Define *overhead fraction* $= \frac{\text{overhead/control-flow work}}{\text{useful work from loop body}} = \frac{(n/G-1)S}{nI} = (\frac{n}{G} - 1) \frac{S}{nI} = (\frac{n - G}{G}) \frac{S}{nI} = \underbrace{(\frac{n-G}{n}) \frac{S}{GI} \approx \frac{S}{GI}}_{G \ll n \implies (\frac{n-G}{n}) \approx 1}$
		- Want to keep this below ~$10\% \rightarrow$ Pick $G$ s.t. $0.1 \ge \frac{S}{GI} \implies G \approx 10\frac{S}{I}$
- KEY TAKEAWAY: coarsening recursion trades off parallelism for lower total work (due to lower control loop overhead)
	- You only want as much parallelism as will keep your processors busy
Why simply spawning children iteratively isn't as good as binary divide and conquer spawning:
- Example: Vector Addition, spawning children iteratively
	<center><img src="School Supplements/6.106_cilk_parallel_loop_example_linear_parallelization.png" alt="" style="width:300px; margin-top: 10px"/></center>	
	- Work: $T_1 = n·I + (n/G ~–~ 1)·S$
	- Span: $T_\infty = G \cdot I + n/G \cdot S$    (longest path highlighted in yellow)
	- Parallelism:  $\frac{T_1}{T_\infty} = \frac{n·I + (n/G ~–~ 1)·S}{G · I + n/G·S}$  compared to  $\frac{n·I + (n/G ~–~ 1)·S}{G · I + \log(n/G)·S}$ from divide and conquer approach
		- Smaller parallelism
		- Intuition: spawn chain is a long series chain instead of a balanced tree; span is much longer.
			- This makes a difference if $S$ is reasonably large compared to $I$ to matter
Practical Tips:
- Minimize span to maximize parallelism
- Try to generate ~10x parallelism
- If you have tons of parallelism, trade if off to reduce work overhead
- Avoid spawning in a loop; use `cilk_for` or use divide-and-conquer
- Parallelize outer loops instead of inner loops (so each chunk is larger)

Analysis:

IDEA: the $\Theta(n)$ merge procedure really kills parallelism -- can we parallelize the `merge` to make it faster?
- Key idea: apply more recursive divide & conquer
			<center><img src="School Supplements/6.106_example_parallel_merge_sort_parallel_merge.png" alt="" style="width:400px; margin-top: 10px"/></center>	
	- Suppose we merge $A$ w/ $B$ where `len(A) >= len(B)`:
	- Pick median of $A$, `ma`, as pivot. Binary search $B$ for the location $A$'s median should be added; call this `mb`
	- Recursively merge `A[<=ma]` with `B[<=mb]` and `A[>ma]` with `B[>mb]`
- Parallel `merge` procedure analysis:
	- Span: $T_\infty(n) = \Theta(\log^2 n)$ (analysis omitted)
- Full merge sort (with parallel `merge`) analysis:
	- Span is now: $T_\infty(n) = \underbrace{T_\infty(n/2) + \Theta(\log^2 n) = \Theta(\log^3 n)}_{\text{By Master Theorem Case 2}}$
	- Parallelism: $\frac{T_1}{T_\infty} = O(n / \log^2 n)$ -- a little better!

Work Efficiency
- $T_S(n)$ = work of best serial program
- $T_1(n)$ = work of parallel program
- *Work Overhead* of parallel program is $\lambda(n) = T_1(n) / T_S(n)$
	- *Work Efficient*: if $\lambda(n) \approx 1$, i.e. $T_1(n) \approx T_S(n)$
	- *Asymptotically Work Efficient*: if $\lambda(n) = \Theta(1)$
- Work Overhead $\lambda$ measures the factor of wasted processing power:
	- Recall Work Law: $T_p \ge \frac{T_1}{P} = \lambda \frac{T_S}{P}$
	- Recall, for linear speedup, we want $T_P = \frac{T_S}{P}$
- KEY TAKEAWAY: make sure your parallelized program doesn't do significantly more work than the serial version, i.e. keep $\lambda$ small
	- if $\lambda$ isn't a constant (i.e. has a factor of $n$), you can be sure your parallel algorithm will suck.
	- <sup><sub>Note: some serial algorithms are not parallelizable (have serial dependencies); to parallelize them, you must use a different algorithm entirely (w/ a different serial projection). In this case, λ may not be constant.</sup></sub>

		- "pd" = "packed double-precision (64-bit float)"
		- "si" = "one int (scalar)" (this is used often in AVX512)
- Important Instructions:
	- Arithmetic/Logic:
		- `__m512i _mm512_set1_epi64(double a)`: broadcast `a` to all lanes
		- `__m128i _mm_add_epi32(__m128i a, __m128i b)`: vectorized add
		- `__m256i _mm_mul_epi32(__256i a, __256i b)`: vectorized multiply; multiplies 4x 32-bit ints, produces 4 64-bit ints
			- IMPORTANT: interprets `a` and `b` as 8-lanes of 32-bit signed ints, but only uses values 0, 2, 4, 6:
				- `a = [a0, -, a2, -, a4, -, a6, -]`
				- `b = [b0, -, b2, -, b4, -, b6, -]`
				- interprets output as 4-lanes of 64-bit signed ints
			- This is because multiplication of ints usually produces much larger ints
	- Compare:
		- `__m128 _mm_cmp_ps(__m128 a, __m128 b, const int imm8)`: vectorized compare
			- `imm8` can take values from 0-31 mapping to different types of comparisons
			- `a`, `b` interpreted as 4x lane 32-bit floats
			- output is a 4x lane where each lane is either `0xFFFFFFFF` or `Ox00000000` if comparison is True or False
	- Loads/Store:
		- `__m256 _mm256_loadu_ps(float const * mem_addr)`: Loads 256 bits (as 8x consecutive 32-bit floats) from `mem_addr`
			- Returns the 8 floats packed in a `__m256` register
			- NOTE: the `u` at the end of `loadu` indicated "unaligned" write -- the address does not need to be a multiple of 32.
		- `void _mm256_storeu_ps(float *mem_addr, __m256 a)`: Writes 256 bits to `mem_addr` 
		- Stream writes: 
			- Normally, during a write, you need to first read the line from cache/memory, write the part you want to write, *then* write the whole line back into cache
			- Stream writes are applicable if you are overwriting an entire cache line; just skips the loading step and writes immediately. ~2x faster
	- Non-SIMD vector ops:
		- Shuffle: mix the lanes of the vector register
		- Unpack: expand the upper N lanes to take the space of the full vector
		- Dot Product: dot products between vectors
		- addsub: Add values from all even lanes; subtract values from all odd lanes

## Linux x86/64 Calling Convention
- Stack grows *down*, heap grows *up*
	- Literally, in address space
			<center><img src="School Supplements/6.106_stack_heap.png" alt="" style="width:200px; margin-top: 10px"/></center>
- Stack variables: func. args, return address, register state (i.e. saved register values to obey caller/callee-saved convention), local variables that don't fit in registers
- Stack is organized into frames; each function gets own frame
	 - `%rbp`: base pointer	
		- points to *top* of current stack frame
		- stationary
	- `%rsp`: stack pointer
		- points to *bottom* of current stack frame
		- grows downward as function puts more things on the stack
	- `%rip`: instruction pointer
		- `call` instruction saves `%rip` onto stack (to save where instruction ptr was prior to the func. call) and then jumps to the func.
		- `ret` instruction pops `%rip` from stack, jumps to `%rip`
	- Maintaining registers across calls
		- Caller responsible for saving some register state to stack (and restoring after the callee is finished) in case callee tries to use them; callee responsible for saving (and restoring, at the end of the function call) some other register states 
				<center><img src="School Supplements/6.106_register_table.png" alt="" style="width:500px; margin-top: 10px"/></center>
	- General Structure of a Function:
			<center><img src="School Supplements/6.106_function_structure.png" alt="" style="width:200px; margin-top: 10px"/></center>
		1. Store current base pointer (representing the anchor of the caller's stack frame)
		2. Set base pointer equal to stack pointer (setting the top/anchor of the new stack frame)
		3. Save callee-saved registers that the function will use
		4. Store args from caller
		5. Build any local variables/do function logic
		6. If calling another function:
			- Store args for callee
			- jump
		7. If returning:
			- Restore callee-saved registers
			- Restore base pointer
			- `retq`
- Deep Dive [Example](https://godbolt.org/z/xKhj73bdK):
	<center><img src="School Supplements/6.106_fibonacci_godbolt_example.png" alt="" style="width:500px; margin-top: 10px"/></center>
	- Linkage Block (from caller to current func.):
		- `pushq %rbp`: push current value of base pointer to stack (and decrement the stack pointer automatically)
		- `movq %rsp, %rbp`: Set base pointer equal to stack pointer
		- `pushq %rb14`, `pushq %rbx`: just saving values according to callee-saved convention (since the callee tries to use these registers)
		- `movq %rdi, %rbx`: saving value of `%rdi` to `%rbx`, since we need to free `%rdi` for when we do another func. call (`%rdi` is the designated register for the 1st arg. to a func. call)
	- If Statement:
		- `cmpq $2, %rdi`: compare `%rdi` (which holds `n`) to `2`; store result in RFLAG
		- `jl .LBB0_2`: jump to `LBB0_2` if comparison resulted in "less than"
	- Calls to `fib(n-1)` and `fib(n-2)`: 
		- Use either `lea` or `add` to compute `n-1` and `n-2`; store in `%rbx`
			- <sup>(`lea` = "load effective address"; frequently abused to perform arithmetic but using a different part of the CPU than the ALU)</sup>
		- Move `%rbx` to `%rdi` (the register for 1st argument)
		- Then call `fib`
		- Store return value from `rax` to `rbx`
	- Function Postcursor:
		- `popq rb14`, `popq %rbx`: restore callee-saved register values
		- `popq %rbp`: pop base pointer value to where it was before this func. call
		- `retq`

**x86 Architecture**
- 3 core architectural ideas:
	- Parallelism (instruction-level parallelism, pipelining (having each stage of pipeline execute a different instruction at any given moment), multi-code)
	- Locality (use caching to save data that's been recently used, hoping that it'll be used again)
	- Branch Prediction (predict branches and run in advance)
- Pipelining & Dealing w/ Stalls
	- Functional Units
		- Different instructions (i.e. addition vs division) take different # cycles; cause stalls
		- Solution: instead of having a single ALU, split it into multiple "functional units" that can run at the same time
			- Each functional unit can also be pipelined, so it can run multiple instructions in parallel
		- The fetch and decode stages 
	- Branch Predictors
		- Maintain table mapping addresses of branch instructions to predictions of their outcome
	- Dealing with Data Dependencies:
		- 3 types of data dependencies:
			- RAW (Read after Write): Must wait for write to finish before read
			- WAR (Write after Read):  Usually name-dependencies if multiple independent instructions use same register name
			- WAW (Write after Write): Usually name-dependencies if multiple independent instructions use same register name
		- Bypassing:
			- If instruction 2 reads what instruction 1 writes:
							<center><img src="School Supplements/6.106_read_write_stall.png" alt="" style="width:175px; margin-top: 10px"/></center>	
				- This cases a stall until instruction 1 finishes writing to `%rax`
			- Bypassing: allows instruction 2 to read the result of instruction 1 before it's been written to `%rax`
				<center><img src="School Supplements/6.106_bypassing.png" alt="" style="width:450px; margin-top: 10px"/></center>	
		- Register Renaming: Fixes WAW + WAR dependencies by changing which register you're using
			- Intel Haswell has only 16 registers accessible in code, but they map to 168 physical registers to avoid dependencies
		- Out-of-order Execution: Reduces impact of RAW dependencies
			- While Read is waiting for Write to finish, CPU can execute other, independent instructions in the meantime
	- SMT: simultaneous multi-threading
		- 2 instruction streams running at the same time; if one stalls, switch to running the other

## Bentley Rules
**4 Categories of Optimization for reducing "Work"**
Data Structures
- *Packing*: store >1 data value in 1 machine word
```C
	typedef struct {
		int year: 13;  // 13-bit field
		int month: 4;
		int dat: 5;
	} date_t;
```
- *Encoding*: convert data into form that requires fewer bits
- *Augmentation*: add extra info to data structure to make common ops faster
	- i.e. adding both head/tail ptrs to linked list if doing lots of list concat
- *Caching*: avoid unnecessary recomputation
- *Precomputation*: calculate + store lookup table ahead of time to avoid doing them at "test-time"
- *Compile-time Initialization*: Same as pre-computation, but at compile-time (i.e. just hard-coding values)
	- Metaprogramming: Writing program whose output is source code (or i.e. code for a large lookup table) that you paste into your actual program
	- Multi-stage Programming: 
		- `static_var<type>` are evaluated in stage 1 and replaced w/ compiled values
		- `dyanmic_var<type>` are evaluated in stage 2 (u
		- sing stored `static_var<type>` values)
		- i.e. (left: pre-stage 1, right: post-stage 1 -- notice how `setup()` gets compiled into constants)
			<center><img src="School Supplements/6.106_multistage_program.png" alt="" style="width:600px; margin-top: 10px"/></center>	
- *Sparsity*: Avoid storing and computing with 0's
	- Compressed Sparse Rows (CSR)
			<center><img src="School Supplements/6.106_sparsity.png" alt="" style="width:400px; margin-top: 10px"/></center>	
		- `rows`: each index corresponds to a row; value indicates start of a slice into `cols`
		- `cols`: parallel list w/ `vals`; specifies the column that each val goes in (in given row) 
		- `vals`: parallel list w/ `cols`; specifies val (in given column + row)
		- Storage $O(n + nnz)$
		- mat-vec-mul $O(nnz)$
				<center><img src="School Supplements/6.106_sparse_mat_vec_mul.png" alt="" style="width:400px; margin-top: 10px"/></center>	
Logic
- *Constant Folding & Propagation*: during compilation, eval constant expressions, substitute results into code (usually done by compiler)
- *Common Sub-expression Elimination*: avoid computing same expression multiple times; instead, cache and substitute (usually somewhat done by compiler)
- *Algebraic Identities*: simplify algebraic formulas
- *Create a Fast Path*: run a quick check first (that passes most of the time) before running complete, thorough check (if the first check fails)
- *Short-Circuiting*: stop/break as soon as you know the answer
- *Ordering Tests*: run tests first that are more likely to allow breaking/stopping before running other tests
	- i.e. Skydio's sample selection
- *Combining Tests*: replace branching/casework (incurs overhead) with computation + lookup array or a switch statement
Loops
- *Loop Unrolling*: unroll multiple iterations of loop into a single iteration
	- avoid overhead from branching/control
	- allow compiler to do more optimization within a single iteration
- *Hoisting / Loop-Invariance Code Motion*: move loop-invariant code (i.e. code that generates the same result every iter of the loop) outside of the loop
- *Loop Fusion / Jamming*: if you have multiple loops over same indices, combine them into 1 loop
Functions
- Functions incur branching/control overhead
- *Inlining*: Don't use function; just inline its body
	- Reduces control flow overhead + allows compiler to do more optimization
	- The compiler does this for you using `inline void func(...)` keyword
	- Basically always good, unless this induces massive code size blowup (i.e. if the function is called in a loop w/tons of iters)
- *Tail-Recursion Elimination*: If the last call in a function is a recursive self-call, avoid the self-call by simply branching back to the top of the function
- *Coarsening Recursion*: Increase size of the base-case to reduce amount of recursion
	- i.e. for small inputs, use non-recursive, faster special case to solve. Only call recursion for large inputs


## C Tricks
- NOTE: good practice to always use `unsigned` types if doing bit hacks
- Get an all 1's mask: `-1` (recall 2's complement representation of negative numbers)
- Set k<sup>th</sup> bit: `x | (1 << k)`
- Clear k<sup>th</sup> bit: `x & ~(1 << k)`
- Toggle the k<sup>th</sup> bit: `x ^ (1 << k)`
- Extract a bit field: `(x & mask) >> shift`
	- (`mask` indicates the bit field to be extracted, `shift` shifts this bit field in the LSB)
		<center><img src="School Supplements/6.106_extract_bit_field.png" alt="" style="width:400px; margin-top: 10px"/></center>	
- Set a bit field: `(x & ~mask) | (y << shift)`
	- (`mask` indicates the bit field, `y` is the value to set it to)
				<center><img src="School Supplements/6.106_set_bit_field.png" alt="" style="width:525px; margin-top: 10px"/></center>	
	- Safer version: `(x & ~mask) | ((y << shift) & mask)`
		- (Mask `y` before ORing with `x` to prevent flipping incorrect bits (highlighted pink))
						<center><img src="School Supplements/6.106_set_bit_field_safe.png" alt="" style="width:525px; margin-top: 10px"/></center>	
- Circular Buffer (more like a modulo $2^k$): 
	- `mask = ((1 << k) - 1)`
	- `x = (x + 1) & mask`
	- This is much more efficient than a `%` operator					<center><img src="School Supplements/6.106_circular_buffer.png" alt="" style="width:425px; margin-top: 10px"/></center>	
- Mask for Least-significant 1
	- `mask = x & (-x)`
	- Why this works: `-x = ~x + 1` (2's complement representation of negative ints)
			<center><img src="School Supplements/6.106_least_significant_1.png" alt="" style="width:300px; margin-top: 10px"/></center>
		- Both `x` and `-x` end up having the same least significant 1

		- Special case for `x=0`
		- Otherwise, we use 2's complement logic; `x & (-x)` returns just the least significant 1 of `x`.

	- `int n_pad = ((n + m-1) / m) * m`
		- Basically ceiling integer division by `m` (and then multiple by `n` after)
- Swapping 2 variables
	- `x = x ^ y`
	- `y = x ^ y`
	- `x = x ^ y`
	- Why this works: `XOR` is its own inverse: `(x ^ y) ^ y = x`
	- HOWEVER: bad for instruction-level parallelism; must happen serially
	- Using a temporary variable is actually faster
- Min of 2 ints
	- Simple method: `r = (x < y) ? x : y`
	- `r = y ^ ((x ^ y) & -(x < y))`
		- `(x < y)` returns 1 if `x < y`, else 0. Then, the minus sign turns this into all 1's (an all-1 mask) or all 0's.
		- if `x < y`:
			- `r = y ^ (x ^ y) = x`
		- if `x > y`:
			- `r = y ^ ((x ^ y) & 0) = y`
		- Good if branch is unpredictable, you want to avoid branching
	- NOTE: in practice, `r = a ? x : y` are optimized by compiler to use `cmov` instruction, so are actually very fast
- Modular Addition
	- `r = (x + y) % n`, where `0 <= x < n`, `0 <= y < n`
	- Want to avoid branching, and want to avoid division
		- `z = x + y`
		- `r = z - (n & -(z >= n))`
			- If `z >= n`, then `r = z - n`. If `z < n`, then `r = z`.
- Modulo powers of 2
	- `r = x % n` where `n` is a power of 2
	- `r = x & (n-1)` is equivalent

## Review
- Intuition of subtracting 1:
	- `10110000` --> `10101111`
	- essentially remove the last 1, then replace all the trailing 0's with 1's
- 2's complement:
	- Leading 1 is negative valued; all other digits positive valued
	- To find 2's complement representation, this is a simple trick: `-x = ~x + 1`
		1. Represent `+x` in binary
		2. Flip all the bits
		3. Add 1
	- i.e.: to represent -28:
		- +28 in binary: `00011100`
		- ~28: `11100011`
		- ~28 + 1: `11100100`   <--   -28 in binary
- Speculative branch prediction
	- Keeps history of running this branch in the past -- repeats most common from history
	- Note: branch mis-prediction is costly -- on order of an L2 cache miss
