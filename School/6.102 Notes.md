
## Style
- Don't modify func. params; make them `const` if possible
- `null` is not allowed as param or return (this is an automatic/assumed precondition)

## Snapshot Diagrams
- Double circle = immutable

## Mutable Types
- **Defensive Copying**: make function always return *copy* of an important object so future clients can mutate the copy safely
- Always opt for built-in immutable types (string, number); use Readonly arrays/sets/maps if possible
- Always assume mutation of inputs is not allowed, unless specified in func. spec

## Function Specs
- *Signature* (name, params, returns)
	- NOTE: do NOT include types here (or repeated info in the actual func. signature)
- *requires*: describe additional restrictions on params
- *effects*: describe return val, exceptions. Any mutation of inputs MUST be stated.
- *Precondition*: responsibility of the client -- satisfy function's *requires* and input types
- *Postcondition*: responsibility of the implementor -- function should satisfy its *effects* and return types **(conditioned on *precondition* being satisfied)**
- NOTE: func. signature is both part of precondition and postcondition
- Make implementation invisible in the spec
- Best to fail fast for inputs not satisfying the spec. For library/widely used funcs, use few preconditions but throw exceptions for invalid inputs
- **Deterministic** Specs (vs "underdetermined"): Outcome entirely determined by input (when satisfying precondition)
- **Declarative** Specs (vs Operational): 
	- Operational: series of steps function performs (i.e. pseudocode)
	- Declarative: only properties of outcome (***PREFERRED*** -- usually shorter, easier to understand, don't inadvertently suggest implementation details that clients may rely on when they aren't part of the actual spec)
- **Strength**: S2 *stronger* than S1 if implementations satisfying S2 all satisfy S1
	- *Stronger Precondition* = fewer valid inputs
	- *Stronger Postcondition* = fewer valid outcomes
	- S2 stronger than S1 iff S2's precondition weaker (same or more allowed inputs), S2's postcondition stronger *for inputs satisfying S1's precondition* (fewer allowed outcomeS)
	- NOTE: when updating a function, you can weaken precondition or strengthen post-condition w/out affecting clients
	- NOTE: S1, S2 can also be *incomparable* if neither is stronger than the other

## Static Checking
- Compile-time checking
- TS is static-checked, *not* dynamically checked (no runtime errors -- only "undefined" values)
- Mutation:
	- immutable = value cannot be changed
		- specific to the type (i.e. Strings are immutable; when you modify a string variable, you re-assign it)
	- constant = variable cannot be re-assigned
		- `const n: number = 5
		- Arrays often defined `const` if you never re-assign the array (you can still push/splice/mutate it)

## Testing
- *Validation*: process of uncovering problems in a program
	- *Verification*: formal reasoning/proof that program is correct
	- Code Review
	- Testing: running on selected inputs, checking results
- ALL TESTS MUST FOLLOW FUNC. SPEC.
- Test-First Programming:
	1. Write spec (func. signature, comments)
	2. Test/write test clients
	3. Implement (anything in function body)
- Systematic Testing:
	- *Correct*: accepts any legal implementation of the spec
	- *Thorough*: find bugs
	- *Small*
- Partition the input space
	- Include boundary conditions as separate measure zero partition
	- Problem: exponential blowup of # testcases with # parameters (if you handle all boundary cases for each parameter)
		- i.e.: 36 test cases for 2 inputs:
			<center><img src="School Supplements/6.1020_partition.png" alt="" style="width:300px; margin-top: 10px"/></center>
		- Solution: multiple partitions. Partition `a`, `b` separately; only require test cases in each subdomain independently rather than in every combination
		- Also introduce 3rd partition for interaction btwn `a`, `b` to ensure coverage of their interaction
						<center><img src="School Supplements/6.1020_triple_partition.png" alt="" style="width:300px; margin-top: 10px"/></center>
- *Blackbox Testing*: Test cases without knowledge of implementation
- *Glassbox Testing*; Test cases with knowledge of implementation, specifically to test edge cases based on implementation
- Coverage
	- *Statement Coverage*: every statement run by at least one test case
	- *Branch Coverage*: every control branch run
	- *Path Coverage*: every possible combination of branches run
	- Practically: shoot for *statement coverage*
- *Regression Test* case: when you find and fix bug, add it to test suite; prevents re-introducing the bug later
- *Fuzz Testing*: random inputs, verify no crashes
- *Property Testing*: random inputs, verify results satisfy some *property* (weaker than the function's desired output property)

## TypeScript
Infra
- Node.js: JavaScript interpreter. `node` runs a JavaScript file
- `npm`: Manages external packages and runner of other tools, i.e. `npm test` for compiling + running test suite
	- Configured in `package.json`
	- `npm install` packages are stored in `node_modules` folder, usually one per project (so each project's environment is isolated)

`===`, `!==`: enforce strict equality
- `==`, `!=` do not, performing hidden type conversions; i.e. `0 == "0"` returns True. Avoid using these
- Note: can use `b ? x : y` statements

Logging
- `console.log("My name is " + name);`
- `console.log("My name is ", ${name})`

Arrays
```ts
let array: Array<type> = [];
array.push(x)
array.pop()  // Del last
array.splice(i, 1)  // Remove element at idx i
array.slice(i, j)  // Shallow copy of array[i : j]
array[i]
array.length
// NOTE: if (!array) doesn't work; arrays are always "True"

// Iterating:
for (const num of numbers) {  // Declare const to avoid accidentally mutating num
    ...
}

for (const [ii, city] of cities.entries()) {
    ...
}
```
- Note: indexing into non-existent index gives "undefined"
- Note: arrays are *sparse* -- you can assign index `j > i` even if index `i` isn't assigned
- Immutable version: `ReadonlyArray`
	- Note: common pitfall w/`ReadonlyArray`: it is actually an *interface* pointing to a normal `Array` where the interface performs checks to disallow mutation
	- If the array that the ReadonlyArray were constructed from were mutable, it can be mutated
```ts
let yourArray: Array<number> = [ 1, 2, 3 ]; 
const myArray: ReadonlyArray<number> = yourArray;
// You can still mutate `yourArray`
```

Tests
```ts
describe("Math.max", function() {  // Suite named "Math.max"
  /*
   * Testing Strategy
   * ...
   * Describe your partition on each input variable, and on their combinations that you are covering
   */
  // Each test titled which partition subdomain it covers
  it("covers a > 0, b > 0, a < b", function() {  // Individual unit test in the suite
    assert.strictEqual(Math.max(1, 2), 2);  // First param = func output, Second param = ground truth
  });

  it("covers a > 0, b > 0, a = b", function() {
    assert.strictEqual(Math.max(9, 9), 9);
  });

  it("covers a > 0, b < 0, a > b", function() {
    assert.strictEqual(Math.max(10, -9), 10), "ERROR MESSAGE";
  });
  ...
});
// All tests in the suite run even if one fails
```
- NOTE: `assert.strictEqual()` fails on data structures (arrays, sets, classes)
	- `assert.deepStrictEqual()`: compares contents of arrays, sets, maps containing primitives (numbers/strings)
