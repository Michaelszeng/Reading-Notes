## Software Construction Recipe
**Writing a Method**
1. **Spec.** Write the spec, including the method signature (name, argument types, return types, exceptions), and the precondition and the postcondition as a documentation comment.
2. **Test.** Create systematic test cases
3. **Implement.** Write the body of the method. You’re done when the tests are all passing.

**Writing an abstract data type**
1. **Spec.** Write specs for the operations of the data type, including method signatures, preconditions, and postconditions. Define abstract value space
2. **Test.** Write test cases for the ADT’s operations
3. **Implement.** 
	1. Choose rep -- define private fields, write down the rep invariant and abstraction function as a comment.
	2. Assert rep invariant -- Implement `checkRep()` that asserts rep invariant
	3. Implement operations -- Write method bodies; call `checkRep()` at the end of each.

**Writing a program** (consisting of ADTs and functions)
1. **Choose data types.**
2. **Choose functions.**
3. **Specs.**
4. **Test.**
5. **Implement simply first.**
6. **Iterate**

Note: you may always be bouncing back to prior steps, iteratively.

## Defining Equality
**Immutable Types**
- ***Value Equality***
	- 2 equivalent definitions:
		1. Abstraction Function (AF) Equivalence: `a = b` iff `AF(a) = AF(b)`
		2. Operation Equivalence: `a = b` iff every operation we can apply on `a` and `b` produces same result
	- AF Equivalence and Operation Equivalence are equivalent; if 1 holds then 2 does; if 1 doesn't, then 2 doesn't.
 - ***Reference Equality*** 
	- Whether 2 variables represent same memory
	NOTE: `===` checks *reference equality*
	- There is no built-in value equality operation
	- To check *value equality*, we usually have to write our own `equalValue()` functions in our classes
		- Ensure this follows *equivalent relation*: reflexive, transitive, symmetric
**Mutable Types**
- ***Observational Equality***: Value Equality holds at the current moment
	- Based only on *observers* + `producers`, without calling *mutators*
- ***Behavioral Equality***: Value Equality holds now and forever, even if one object is mutated
	- Basically equivalent to reference equality (and is checked with `===`)
`assert.strictEqual()` vs `assert.deepStrictEqual`
- `assert.strictEqual()` checks `===`
- `assert.deepStrictEqual()` checks every leaf element in the nested data structure for representational equality
	- i.e. `assert.deepStrictEqual(DurationObj1, DurationObj2)` checks all fields of `DurationObj1` and `DurationObj2` for equality
	- DO NOT USE to compare user-defined types (or collections of them) since this essentially compares reps, not abstract value
Hashing and Equality
- If `Eq(k1, k2)`, for whatever type of equality you care about when comparing keys, then you want `hash(k1) === hash(k2)`
	- If this is not upheld, you can have problems like:
		- `insert(k1, v1)`
		- `Map[k2]`  <-- we expect to be able to use `k2` to get `v1` since `Eq(k1,k2)`, but `k2` hashes differently than `k1` so we don't find `v1`.
- What `Eq()` operation you use is up to choice
	- If you choose `k1`equals `k2` by observational equality (i.e. Python):
		- You cannot allow mutable values to be hashable; `k1` might equal `k2` now, but if `k2` is mutated, then `k1`$\ne$ `k2` by observational equality, so `hash(k1) !== hash(k2)`
		- (i.e. how lists/mutable objects aren't hashable in Python)
	- If you choose `k1` equals `k2` by behavioral equality (i.e. `k1 === k2`) (i.e. TypeScript):
		- All values are hashable; if `k1 === k2`, even if `k2` changes, `k1 === k2` still holds, so `hash(k1) === hash(k2)` still holds
		- NOTE: this has limitations; non-primitive immutables are not useful as keys because, even two copies of an identical object (which are not behaviorally equal) will produce different hash values (you probably want them to be)

- Note: "mutable user-defined types" are "hashable" in the sense that: if you mutate `obj`, `obj` will continue to hash to the same hash value as before the mutation. (But, if you had `obj1` and `obj2` that are copies of each other, they will still hash to different hash values).

## Mutable Types
- **Defensive Copying**: make function always return *copy* of an important object so future clients can mutate the copy safely
- Always opt for built-in immutable types (string, number); use Readonly arrays/sets/maps if possible
- Always assume mutation of inputs is not allowed, unless specified in func. spec

## Inheritence
### Interfaces
- List of method signatures without method bodies
- Class `implements` interface if it provides bodies for all of interface's methods
- Interface cannot be instantiated with `new`
- Interface has no *representation* (no rep invariants, no abstraction funcs.)
- Benefits:
	- Provides clean contract for client, without any implementation information
	- Can have multiple implementations/classes implementing the interface
- If `B` implements `A`, `B` is a *subtype* of `A`
	- `B`'s specifications are all stronger than `A`
- You can have interfaces `extends` other interfaces
- Practical Notes:
	- classes implementing an interface can use `@inheritdoc` for its functions to inherit the specification from the interface
	- Use a factory function that provides a quick way to swap out the underlying implementation of an interface:
	```ts
	/**
	 * @param s 
	 * @returns MyString representing the sequence of characters in s
	 */
	function makeMyString(s: string): MyString {
	    return new ConstructorForAnImplementationOfInterfaceMyString(s);
	}
	```
**Structural Subtyping**
- `B` doesn't `extends` or `implements` `A`, but still provides all operations required by `A`
- Typescript automatically detects this + allows you to use `B` as an instance of `A`

### Subclasses
- Automatically inherit methods of superclass + private representation
- Subclass spec is stronger than superclass
- DANGER: rep-exposure/dependence between sub/super classes
- Variables can have separate *static* and *dynamic types* (dynamic type must be subclass of static type)
	- *dynamic type*: type of object at runtime
	- *static type*: type that object is declared with
	- *Dynamic Dispatch*: How TypeScript determines which implementation of a method to use; picks the implementation of the *dynamic type*
		- i.e.:
		```ts
		const obj: Object = new FastMyString("hello");
		obj.toString() → ?  // This will use FastMyString's toString implementation since FastMyString is the dynamic type (Object) is the static type
		```
		- NOTE: static checking uses object's static type
			- i.e. `obj.charAt(0)` would not compile, since `obj`'s static type is `Object` which doesn't have `charAt()` func.

### Generic Types
- Placeholder type to be filled in later (i.e. `Set<T>`)
- Functions can use generic types:
	```ts
		function assertDefined<T>(val: T | undefined, message?: string): T {
		  return val ?? assert.fail(message);
		}
		
		const temperatures = [99.4, 95.2, 100];
		const firstTemp: number = assertDefined(temperatures[0]); // temperatures[0] has type number|undefined
	```
- Factory function for a generic typed class:
```ts
	// Caller doesn't need to know about the underlying implementation of MySet<Element> used
	function emptySet<Element>(): MySet<Element> {
		return new SimpleSet<Element>(); // concrete subclass chosen here  
	}
	// Example calling: const s1: MySet<number> = emptySet();
```

### Abstract Data Types
- **==Abstraction==.** Hiding low-level details with a simpler, higher-level idea.
- **==Information hiding==.** Hiding details of a module’s implementation from the rest of the system; those details can be changed later w/out changing the rest of the system.
- **==Encapsulation==.** Building a wall around a module so that the module is responsible for its own internal behavior, and bugs in other parts of the system can’t damage its integrity.
- **==Separation of concerns==.** Making a feature (or “concern”) the responsibility of a single module, rather than spreading it across multiple modules.
- Core idea: a type is characterized by its **abstraction***: its operations/functions/public interface. 
	- ***representation***: actual internal data structure + attributes
	- Classes of Operations:
		- *Creators*: create new objects of the type.
		- *Producers*: create new objects of the type, but require one or more existing objects of the type as input.
			- Note: comparison functions (i.e. `x.equals(y)`) are valid producers/operators
		- *Observers*: takes object of the type, returns objects of a different type.
		- *Mutators*: change objects. (ONLY APPLIES TO MUTABLE TYPES)
	- Example: Array (mutable)
		- creators: `Array` constructor, `[ _item1_, _item2_, _etc._ ]` literal syntax, [`Array.of`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Array/of), [`Array.from`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Array/from)
		- producers: [`Array.concat`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Array/concat), slicing
		- observers: `length`, `[..]` indexing syntax
		- mutators: `push`, `pop`, `shift`, `unshift`, [`reverse`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Array/reverse), [`sort`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Array/sort)
	- Good Practice:
		- simple, few operations
		- ***representation independent***
	- Testing: just need to test all its operations.
		- NEVER partition on internal representation details
		- Partition on how this instance was constructed
		- Partition on public-facing properties of the class that are expressible through public spec (i.e. via observers)
	- Good practices: `private` + `readonly`
	- CAREFUL: if returning references to mutable attributes, then clients could modify that attribute
		- ***Instead, use defensive copying in constructor (if taking in a mutable reference) and when returning the value of an attribute in any helper func.***
- **Abstraction Functions** & **Rep Invariants**
	- Abstract value space = set of values that the abstract type is designed to support
	- Representation value space = set of objects that actually implement the abstract values (based on chosen implementation)
	- Rules:
		- every abstract value has some rep value mapping to it (i.e. has a representation)
		- multiple rep values can map to the same abstract value
		- not all rep values map to an abstract value
	- Example: Abstract Value Space = Sets of chars. Representation Value Space = Strings
							<center><img src="School Supplements/6.102_abstraction_rep_values.png" alt="" style="width:350px; margin-top: 10px"/></center>

		- It's possible to have strings that are illegal for the give abstract type
	- ***Abstraction Function***: maps rep value to abstract value
		- There are many possible abstraction function maps + rep invariants -- the user must design this
	- ***Rep Invariant***: maps rep values to boolean (True/False maps to an abstract value)
		- NOTE: good practice to assert rep invariants at the end of every op that mutates the rep (or at the end of literally every function for defensive programming)
	- Both should be documented in code next to the representation itself, along w/justification of why the rep is safe from exposure to clients:
	```ts
	class CharSet {
	    private s: string;
	    // Rep invariant:
	    //   s contains no repeated characters
	    // Abstraction function:
	    //   AF(s) = {s[i] | 0 <= i < s.length}
	    //   NOTE: ALWAYS USE ACTUAL FUNCTION NOTATION HERE
	    //
	    // Safety from rep exposure:
	    //   All fields are private;
	    //   author and text are Strings, so are guaranteed immutable;
	    //   timestamp is a mutable Date, so Post() constructor and getTimestamp()
	    //        make defensive copies to avoid sharing the rep's Date object with clients.
	}
	```
	- Generally, in the justification of *Safety from rep exposure*, justify that types are either private/immutable or mutable but either is never returned/exposed to the client or is always returned with defensive copying
	- ***Benevolent Side Effects***: If the representation of an immutable object changes (but its abstract value doesn't change)
- Proving invariants about your datatype (using *structural induction*)
	1. established by creators and producers
	2. preserved by mutators, observers, and producers
	3. no rep exposure occurs

## Function Specs
- *Signature* (name, params, returns)
	- NOTE: do NOT include types here (or repeated info in the actual func. signature)
- *requires*: describe additional restrictions on params
- *effects*: describe return val, exceptions. Any mutation of inputs MUST be stated.
- *Precondition*: responsibility of the client -- satisfy function's *requires* and input types
- *Postcondition*: responsibility of the implementor -- function should satisfy its *effects* and return types **(conditioned on *precondition* being satisfied)**
- NOTE: func. signature is both part of precondition and postcondition
- Make implementation invisible in the spec
- Best to fail fast for inputs not satisfying the spec. For library/widely used funcs, use few preconditions but throw exceptions for invalid inputs
- **Deterministic** Specs (vs "underdetermined"): Outcome entirely determined by input (when satisfying precondition)
- **Declarative** Specs (vs Operational): 
	- Operational: series of steps function performs (i.e. pseudocode)
	- Declarative: only properties of outcome (***PREFERRED*** -- usually shorter, easier to understand, don't inadvertently suggest implementation details that clients may rely on when they aren't part of the actual spec)
- **Strength**: S2 *stronger* than S1 if implementations satisfying S2 all satisfy S1
	- *Stronger Precondition* = fewer valid inputs
	- *Stronger Postcondition* = fewer valid outcomes
	- S2 stronger than S1 iff S2's precondition weaker (same or more allowed inputs), S2's postcondition stronger *for inputs satisfying S1's precondition* (fewer allowed outcomes)
	- NOTE: when updating a function, you can weaken precondition or strengthen post-condition w/out affecting clients
	- NOTE: S1, S2 can also be *incomparable* if neither is stronger than the other

## Static Checking
- Compile-time checking
- TS is static-checked, *not* dynamically checked (no runtime errors -- only "undefined" values)
- Mutation:
	- immutable = value cannot be changed
		- specific to the type (i.e. Strings are immutable; when you modify a string variable, you re-assign it)
	- constant = variable cannot be re-assigned
		- `const n: number = 5
		- Arrays often defined `const` if you never re-assign the array (you can still push/splice/mutate it)

## Testing
- *Validation*: process of uncovering problems in a program
	- *Verification*: formal reasoning/proof that program is correct
	- Code Review
	- Testing: running on selected inputs, checking results
- ALL TESTS MUST FOLLOW FUNC. SPEC.
- Test-First Programming:
	1. Write spec (func. signature, comments)
	2. Test/write test clients
	3. Implement (anything in function body)
- Systematic Testing:
	- *Correct*: accepts any legal implementation of the spec
	- *Thorough*: find bugs
	- *Small*
- Partition the input space
	- Include boundary conditions as separate measure zero partition
	- Problem: exponential blowup of # testcases with # parameters (if you handle all boundary cases for each parameter)
		- i.e.: 36 test cases for 2 inputs:
			<center><img src="School Supplements/6.1020_partition.png" alt="" style="width:300px; margin-top: 10px"/></center>
		- Solution: multiple partitions. Partition `a`, `b` separately; only require test cases in each subdomain independently rather than in every combination
		- Also introduce 3rd partition for interaction btwn `a`, `b` to ensure coverage of their interaction
						<center><img src="School Supplements/6.1020_triple_partition.png" alt="" style="width:300px; margin-top: 10px"/></center>
- *Blackbox Testing*: Test cases without knowledge of implementation
- *Glassbox Testing*; Test cases with knowledge of implementation, specifically to test edge cases based on implementation
- Coverage
	- *Statement Coverage*: every statement run by at least one test case
	- *Branch Coverage*: every control branch run
	- *Path Coverage*: every possible combination of branches run
	- Practically: shoot for *statement coverage*
- *Regression Test* case: when you find and fix bug, add it to test suite; prevents re-introducing the bug later
- *Fuzz Testing*: random inputs, verify no crashes
- *Property Testing*: random inputs, verify results satisfy some *property* (weaker than the function's desired output property)
