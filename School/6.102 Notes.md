

## Software Construction Recipe
**Writing a Method**
1. **Spec.** Write the spec, including the method signature (name, argument types, return types, exceptions), and the precondition and the postcondition as a documentation comment.
2. **Test.** Create systematic test cases
3. **Implement.** Write the body of the method. You’re done when the tests are all passing.

**Writing an abstract data type**
1. **Spec.** Write specs for the operations of the data type, including method signatures, preconditions, and postconditions. Define abstract value space
2. **Test.** Write test cases for the ADT’s operations
3. **Implement.** 
	1. Choose rep -- define private fields, write down the rep invariant and abstraction function as a comment.
	2. Assert rep invariant -- Implement `checkRep()` that asserts rep invariant
	3. Implement operations -- Write method bodies; call `checkRep()` at the end of each.

**Writing a program** (consisting of ADTs and functions)
1. **Choose data types.**
2. **Choose functions.**
3. **Specs.**
4. **Test.**
5. **Implement simply first.**
6. **Iterate**

Note: you may always be bouncing back to prior steps, iteratively.

## Style
- Don't modify func. params; make them `const` if possible
- `null` is not allowed as param or return (this is an automatic/assumed precondition)

## Message-Passing + Client/Server
### Concurrency
2 models:
- *Shared memory*
- *Message passing*
	- Greater safety from bugs: messages an immutable, no danger of inadvertently changing shared memory 
*Process*: instance of running program w/ private memory space. A virtual computer.
*Thread*: a place program is being run, i.e. a stack frace. A virtual processor.
- Processes contain threads
- Automatically shares all memory w/other threads
*Time Slicing*: processor scheduling between threads.
Typescript Workers (i.e. processes)
```ts
let worker: Worker = new Worker('./hello-world.js');  // Give a js file to run in the worker
```
- Use `SharedArrayBuffer` for shared memory/binary data (memory is otherwise isolated)
- Bidirectional message channel automatically made when `Worker` is created
- Note: throwing error in 1 worker terminates the main process

### Client/Server
- IP address: identifies a machine
- Port: 
	- Servers can decide what each port does/publish certain data there
	- Servers generally only allow one client to connect/listen to each port
- Most web servers return HTML
- Most web APIs return JSON
- Routes + Parameters call different functions in web API
	- Path Parameters: (after `/`) [`https://api.weather.gov/points/42.3541,-71.1104`](https://api.weather.gov/points/42.3541,-71.1104)
	- Query Parameters (after `?`): [`https://api.weather.gov/alerts/active?area=MA&severity=Minor`](https://api.weather.gov/alerts/active?area=MA&severity=Minor)
- GET vs POST:
	- GET requests -- observer operations, does not mutate server state
	- POST requests -- mutate server state, can have additional request body with JSON data
- HTTP responses (to GET/POST requests):
	- 200 OK
	- 404 Not Found
	- 400 Bad Request (parameters bad)
	- 500 Internal Server Error (something else went wrong)
	- Can have body (HTML, plain text, JSON)

## Promises
- `Promise<T>`: Special type that can be `await`ed for value
```ts
// Start background task
const promise: Promise<string> = fs.promises.readFile('account', { encoding: 'utf-8' });

// Wait for background task finish (either returns value for `data` or throws exception)
const data: string = await promise;
```
- NOTE: `await` is a "check and yield" operation
	- 
- Empty Promise (`void` return type):
```ts
const promise: Promise<void> = timeout(2000);
// started up a timer for 2000 milliseconds

await promise;
// no useful return value, but -- now we know that 2000 milliseconds have indeed passed
```
Combining promises
- Wait for all promises to be fulfilled, return array of results:
```ts
const allResponses: Array<Response> = 
  await Promise.all( [ fetch('http://www.mit.edu/'),
                       fetch('http://www.harvard.edu/'),
                       fetch('http://www.tufts.edu/') ] );
```
- Wait until first promise is successfully fulfilled, return it:
```ts
const firstResponse: Response = 
  await Promise.any( [ fetch('http://www.mit1.edu/'),
                       fetch('http://www.mit2.edu/'),
                       fetch('http://www.mit3.edu/') ] );
```
- Wait until first promise successfully fulfilled or fails with Error:
```ts
// Useful for timeouts
const responseOrTimeout: Response|void =
  await Promise.race( [ fetch('http://www.mit.edu/'), 
                        timeout(5000) ] );
```
`then`
- You define a lambda function to happen after the promise finishes (and this combined promise + lambda function afterwards is a new promise)
```ts
const promisedResponse: Promise<Response> = fetch('http://www.mit.edu/');

// After promisedResponse fulfills, extract the text and return the text
const promisedText: Promise<string> = 
  promisedResponse.then(function(response: Response): Promise<string> {
    // we've made a connection, which is why the `response` object exists
    const downloadingPromise: Promise<string> = response.text();
    // but we may have to wait some more for the actual data, hence `downloadingPromise`
    return downloadingPromise;
  });
```
- NOTE: `then` always calls its callback asynchronously; its callback gets added to the event queue once the promise is finished; thus, the line of code after `promise.then(...)` may run before the callback in `then`

### Async Functions
- `async` keyword
	- Return type must be `Promise<T>`
	- Indicates to JS runtime that the function should yield if its `await` is not ready yet
```ts
async function async_f(): Promise<T> {
	ret = await async_f2();
	// If something bad happens:
    throw new Error('account does not contain a number');
    // Else, return value of type T
    return ret;
}

// Caller must call async function using promise API:
const x = await funct();
```
- Sync vs Async:
	- Synchronous func. runs 1 time to completion
	- Asynchronous func. may yield many times (returning pending Promises) during pending `await`s, only proceeding when `await` is finished
- How async func. works under the hood:
	- upon hitting a pending `await`, the rest of the function body gets wrapped into a callback that is called/added to the event queue once the await finishes
- **If func. A calls `await` on an async func. B, func. A must be async too** (or a static error is thrown)
	- This is a quirk of JS:
		- *Cooperative/Non-Preemptive* Concurrency Model
			- JS is single-threaded + handle an event loop (i.e. to handle button clicks, etc. on web)
				- Repeatedly checks an event queue for events
			- Thus, all sync and async functions are expected to return very quickly
	- The JS backend, until `await async_f2()` has finished, yields from `async_f()` with a pending promise as well
		- Meanwhile, it gives main thread control back to caller (until `async_f2()` finishes)
		- Notably, `await async_f2()` doesn't actually block the main thread; it "checks and yields" thread control to its caller
	- A sync function can't call `await` because only `async` functions are allowed to yield early with a pending promise
		- sync functions (by defn.) must run to completion without giving up main thread control

### Resolvers
`Promise<T>` are not mutable, but `Promise.withResolvers()` creates a `promise` object + `resolve`, `reject` functions:
```ts
/**
 * @param milliseconds duration to wait
 * @returns a promise that is fulfilled with void `milliseconds` after timeout() was called
 */
function timeout(milliseconds:number):Promise<void> {
    const { promise, resolve, reject } = Promise.withResolvers<void>();
    setTimeout(resolve, milliseconds);
    return promise;
}
```
- The "promiser" (i.e. the `timeout` func.) has access to `resolve` and `reject`
- The receiver of the promise (i.e. caller of `timeout`) does not

## Debugging
**Gallery of Bugs**
- *Aliasing Bug*: 2 vars alias to same obj
- *Off-by-one Bug*: 
	- 0- vs 1-indexing
	- loop termination (`<` vs `<=`)
	- fencepost bugs (fence with `n` posts --> `n-1` fences)
- *Ordering Bug*: 
	- conventions on whether x or y axis comes first, orientation/origin of axes
	- `copy(to, from)` vs `copy(from, to)` convention
- *Mutating-while-iterating Bug*:
	- mutating array while iterating through its elements
**Avoiding Bugs**
- dynamic checking (fail fast on invalid inputs)
- immutable/const values
- *Encapsulation*: ensuring no external modules can impact behavior of a given module
	- use `private`
	- control/minimize variable scope
		- use `let` instead of `var` (`var` automatically sets variable scope to surrounding function, ignoring `{}` braces)
**How to use Assertions**:
- check argument preconditions
- check function post-conditions
- assert rep-invariant
- What NOT to assert:
	- conditions external to the program (i.e. existence of files) -- assertions should only test *internal* state
	- check external conditions by raising exceptions (if they're not met)
Debugging Tips:
- Progress log:
	- "hypothesis, experiment, outcome" loop
- Keep a bug list/don't get distracted from the main bug you're trying to fix
- Probe for root cause rather than patch a fix that seems to workf

## Grammars
*Grammar*: defines a set of strings
- *Terminals*: Written in quotes; can't be expanded any further (i.e. `'http'`)
- *Nonterminals*: Variables that could represent any string in a set of strings
	- *Root*: the main variable/non-terminal
- *Productions*: rules that define nonterminals
- Example: grammar with nonterminal `url`, consisting of only one terminal `'http://mit.edu'`
```ts
url ::= 'http://mit.edu'
```
Operators
- Repetition
```ts
x ::= y*  // x matches zero or more y
```
- Concatenation
```ts
x ::= y z  // x matches y cat z
```
- Union
```ts
x ::= y | z  // x matches 
```
- Can define more complex grammars: nonterminal `url` can be 3 possible terminals
```ts
url ::= 'http://' hostname '/'
hostname ::= 'mit.edu' | 'stanford.edu' | 'google.com'
```
- Example: all possible URLs:
```ts
url ::= 'http://' hostname '/'
hostname ::= word '.' word  // i.e. "mit.edu"
word ::= letter letter*  // Require word to have at least one letter
letter ::= ('a' | 'b' | 'c' | 'd' | 'e' | 'f' | 'g' | 'h' | 'i' 
                | 'j' | 'k' | 'l' | 'm' | 'n' | 'o' | 'p' | 'q' 
                | 'r' | 's' | 't' | 'u' | 'v' | 'w' | 'x' | 'y' | 'z')
```
More Operators
- 0 or 1 occurrence
```ts
x ::= y?  // x is y or ""
```
- 1 or more occurrences
```ts
x ::= y+  // equivalent to x ::= y y* 
```
- Exact number of occurrences
```ts
x ::= y{3}  // equivalent to x ::= y y y

x ::= y{1,3}  // equivalent to x ::= y | y y | y y y

x ::= y{,3}  // equivalent to x ::=  | y | y y | y y y   (can be empty string too)

x ::= y{2,}  // equivalent to x ::= y y y*
```
- Character class
```ts
x ::= [aeiou]     // equivalent to  x ::= 'a' | 'e' | 'i' | 'o' | 'u'
x ::= [a-c]       // equiavlent to  x ::= 'a' | 'b' | 'c'
```
- Inverted character class
```ts
x ::= [^a-c]      // x is any char but 'a', 'b', 'c'
```
- Equivalent grammar for all possible URLs:
```ts
url ::= 'http://' hostname '/'
hostname ::= word '.' word
word ::= [a-z]+
```
Recursive Grammars:
- Example: URLs with any number of segments (i.e. `http://didit.csail.mit.edu`)
```ts
url ::= 'http://' hostname '/' 
hostname ::= word '.' hostname | word '.' word
word ::= [a-z]+
```

### Regular Expressions (Regex's)
- A grammar is *regular* iff you can remove all non-terminals but the root; i.e. squeeze the grammar into one line *without* recursion:
```ts
url ::= 'http://' ([a-z]+ '.')+ [a-z]+ (':' [0-9]+)? '/' 
```
- *Regular Expression*: simplified grammar with only terminal characters, parentheses for order of ops, operators
	- Have additional special characters:
```ts
.   // matches any single character (but sometimes excluding newline, depending on the regex library)

\d  // matches any digit, same as [0-9]
\s  // matches any whitespace character, including space, tab, newline
\w  // matches any word character including underscore, same as [a-zA-Z_0-9]
\n  // newline
\t  // tab

\.  \(  \)  \*  \+  \|  \[  \]  \\  // "escape" operator if you want to use special characters literally
```
- Example (urls):
```ts
http://([a-z]+\.)+[a-z]+(:[0-9]+)?/
```
Regex's in Typescript:
- Regex's are delimited using `/.../`
- `replace`: 
```ts
const singleSpacedString = s.replace(/ +/g, " ");  // replace all runs of spaces with a single space; the 'g' at the end indicates "global" -- replcae all instances throughout `s`, not just the first instance
```
- `match`:
```ts
if (s.match(/http:\/\/([a-z]+\.)+[a-z]+(:[0-9]+)?\//)) {
    // then s is a url
}
```
- Extraction:
	- Name capturing groups `(?<VARIABLE>...)` -- extract parts of matched string and store in variable
```ts
const s = "2020-03-18";
const regex = /(?<year>\d{4})-(?<month>\d{2})-(?<day>\d{2})/;
const m = s.match(regex);
if (m) {
  assert(m.groups);
  const year = m.groups.year;
  const month = m.groups.month;
  const day = m.groups.day;
  // m.groups.name is the part of s that matched (?<name>...)
}
```

### Parse Generators
Takes a grammar as input, automatically generates a parser.
A parser takes any string and determines if it matches the grammar.
`ParserLib`:
- Example: any string that represents int summation
```ts
import { Parser, ParseTree, compile } from "parserlib";

enum IntegerGrammar {
  Expr, Sum, Primary, Constant, Whitespace
}

const grammar: string = `
  @skip whitespace {
      expr ::= sum;
      sum ::= primary ('+' primary)*;
      primary ::= constant | '(' sum ')';
  }
  constant ::= [0-9]+;
  whitespace ::= [ \\t\\r\\n]+;  // <-- note that backslashes must be escaped here, because this regex is inside a string
`;

const parser: Parser<IntegerGrammar> = compile(grammar, IntegerGrammar, IntegerGrammar.Expr);

// Example use:
const parseTree: ParseTree<IntegerGrammar> = parser.parse("54+(2+ 89)");

/**
 * Convert a parse tree into an abstract syntax tree (i.e. an instance of IntegerExpression).
 * 
 * @param parseTree constructed according to the IntegerExpression grammar
 * @returns abstract syntax tree corresponding to parseTree
 */
function makeAbstractSyntaxTree(parseTree: ParseTree<IntegerGrammar>): IntegerExpression {
    if (parseTree.name === IntegerGrammar.Expr) {
        // expr ::= sum;
        return makeAbstractSyntaxTree(parseTree.children[0] ?? assert.fail('missing child'));
        
    } else if (parseTree.name === IntegerGrammar.Sum) {
        // sum ::= primary ('+' primary)*;
        const children = parseTree.childrenByName(IntegerGrammar.Primary);
        const subexprs = children.map(makeAbstractSyntaxTree);
        const expression: IntegerExpression = subexprs.reduce((result, subexpr) => new Plus(result, subexpr));
        return expression;
        
    } else if (parseTree.name === IntegerGrammar.Primary) {
        // primary ::= constant | '(' sum ')';
        const child: ParseTree<IntegerGrammar> = parseTree.children[0] ?? assert.fail('missing child');
        // check which alternative (constant or sum) was actually matched
        switch (child.name) {
        case IntegerGrammar.Constant:
            return makeAbstractSyntaxTree(child);
        case IntegerGrammar.Sum:
            return makeAbstractSyntaxTree(child);
            // for this parser, we do the same thing either way (and should really DRY this out)
        default:
            assert.fail(`Primary node unexpected child ${IntegerGrammar[child.name]}`);
        }
        
    } else if (parseTree.name === IntegerGrammar.Constant) {
        // constant ::= [0-9]+;
        const n: number = parseInt(parseTree.text);
        return new Constant(n);
        
    } else {
        assert.fail(`cannot make AST for ${IntegerGrammar[parseTree.name]} node`);
    }
}
```
`@skip` operator:
- Allows you to define a regex that will simply be ignored
Parse Trees
- Parsing a grammar can be seen as recursively exploring the parse tree
- *Abstract Syntax Tree*
- *Concrete Syntax Tree*
Abstract Syntax Tree, Recursive datatypes often used to create Internal *Domain Specific Languages (DSLs)*
- *DSL*: language that expresses problems in narrower domain than general-purpose programming language
	- *External DSL*: creates entirely new syntax (i.e. regex, `SQL`)
		- `SQL`, for example, is a language for describing commands you would do on a database
	- *Internal DSL*: uses syntax of existing language (i.e. TypeScript or Python) to express problems in a problem class
		- Usually a recursive data structure (that can be parsed with an abstract syntax tree)
		- i.e. `concat(note(1, C, Piano), concat(note(1, D, Piano), note(1, E, Piano)))` expresses an instance of a Music note sequence "C D E"

## Iterators, Iterables, Generators
*Iterable*: object that implements `Iterable<T>` interface; implementors must have `iterator` (i.e. `__iter__` in Python) method that returns an `Iterator` object for the sequence
*Iterator*: object with a `next()` method that returns the next element and mutates the `Iterator` by incrementing its index.
- A level of abstraction that makes it easy to iterate over all sequence-like datatypes
*Generator*: function that builds an `Iterator`, producing each element of sequence using `yield`
- Must be declared using `function*` instead of `function`
```ts
function* addConstant(sequence: Iterable<number>, k: number): Generator<number> {
  for (const x of sequence) {
    yield x + k;
  }
}
```
- `addConstant()` returns a `Generator`
Important sequence operations:
- `map`: `[1, 4, 9, 16].map(Math.sqrt);` $\rightarrow$ `[1, 2, 3, 4]`
- `filter`: `["x", "y", "2", "3", "a"].filter(s => "abcdefghijklmnopqrstuvwxyz".includes(s)));` $\rightarrow$ `["x", "y", "a"]`

## Defining Equality
**Immutable Types**
- ***Value Equality***
	- 2 equivalent definitions:
		1. Abstraction Function (AF) Equivalence: `a = b` iff `AF(a) = AF(b)`
		2. Operation Equivalence: `a = b` iff every operation we can apply on `a` and `b` produces same result
	- AF Equivalence and Operation Equivalence are equivalent; if 1 holds then 2 does; if 1 doesn't, then 2 doesn't.
 - ***Reference Equality*** 
	- Whether 2 variables represent same memory
	NOTE: `===` checks *reference equality*
	- There is no built-in value equality operation
	- To check *value equality*, we usually have to write our own `equalValue()` functions in our classes
		- Ensure this follows *equivalent relation*: reflexive, transitive, symmetric
**Mutable Types**
- ***Observational Equality***: Value Equality holds at the current moment
	- Based only on *observers* + `producers`, without calling *mutators*
- ***Behavioral Equality***: Value Equality holds now and forever, even if one object is mutated
	- Basically equivalent to reference equality (and is checked with `===`)
`assert.strictEqual()` vs `assert.deepStrictEqual`
- `assert.strictEqual()` checks `===`
- `assert.deepStrictEqual()` checks every leaf element in the nested data structure for representational equality
	- i.e. `assert.deepStrictEqual(DurationObj1, DurationObj2)` checks all fields of `DurationObj1` and `DurationObj2` for equality
	- DO NOT USE to compare user-defined types (or collections of them) since this essentially compares reps, not abstract value
Hashing and Equality
- If `Eq(k1, k2)`, then you want your has function to satisfy `hash(k1) === hash(k2)`
	- If this is not upheld, you can have problems like:
		- `insert(k1, v1)`
		- `Map[k2]`  <-- we expect to be able to use `k2` to get `v1` since `Eq(k1,k2)`, but `k2` hashes differently than `k1` so we don't find `v1`.
- What `Eq()` operation you use is up to choice
	- If you choose `k1`equals `k2` by observational equality (i.e. Python):
		- You cannot allow mutable values to be hashable; `k1` might equal `k2` now, but if `k2` is mutated, then `k1`$\ne$ `k2` by observational equality, so `hash(k1) !== hash(k2)`
		- (i.e. how lists/mutable objects aren't hashable in Python)
	- If you choose `k1` equals `k2` by behavioral equality (i.e. `k1 === k2`) (i.e. TypeScript):
		- All values are hashable; if `k1 === k2`, even if `k2` changes, `k1 === k2` still holds, so `hash(k1) === hash(k2)` still holds
		- NOTE: this has limitations; non-primitive immutables are not useful as keys because, even two copies of an identical object (which are not behaviorally equal) will produce different hash values (you probably want them to be)

## Mutable Types
- **Defensive Copying**: 
	- make function always return *copy* of an important object so future clients can mutate the copy safely
	- make function create a copy when clients pass a mutable object in (so client can't later mutate it and affect the function/class's behavior)
- Always opt for built-in immutable types (string, number); use Readonly arrays/sets/maps if possible
- Always assume mutation of inputs is not allowed, unless specified in func. spec

## Inheritance
### Interfaces
- List of method signatures without method bodies
- Class `implements` interface if it provides bodies for all of interface's methods
- Interface cannot be instantiated with `new`
- Interface has no *representation* (no rep invariants, no abstraction funcs.)
- Benefits:
	- Provides clean contract for client, without any implementation information
	- Can have multiple implementations/classes implementing the interface
- If `B` implements `A`, `B` is a *subtype* of `A`
	- `B`'s specifications are all stronger than `A`
- You can have interfaces `extends` other interfaces
- Practical Notes:
	- classes implementing an interface can use `@inheritdoc` for its functions to inherit the specification from the interface
	- Use a factory function that provides a quick way to swap out the underlying implementation of an interface:
	```ts
	/**
	 * @param s 
	 * @returns MyString representing the sequence of characters in s
	 */
	function makeMyString(s: string): MyString {
	    return new ConstructorForAnImplementationOfInterfaceMyString(s);
	}
	```
**Structural Subtyping**
- `B` doesn't `extends` or `implements` `A`, but still provides all operations required by `A`
- Typescript automatically detects this + allows you to use `B` as an instance of `A`
**Interpreter vs Visitor Pattern**
- Suppose interface `Music` has function `duration()`
	- *Interpreter Pattern*: Each class that implements `Music` writes its own `duration()` function
		- Dynamic Dispatch picks the right version of `duration()` to call at runtime
		- This is "normal"
		- Downside: adding a new operation to `Music` interface --> need to modify every single `Music` subclass
	- *Visitor Pattern*: One separate `MusicVisitor` interface
		- Each operation (i.e. `duration()`) gets a new Visitor subclass that extends `MusicVisitor`
			- This subclass defines the `duration()` function for all subclasses, i.e.:
			```ts
			class DurationVisitor implements MusicVisitor<number> {
			  // Define behavior for each subclass of Music
			  onNote(note: Note): number {  // For Note type
			    return note.duration;
			  }
			
			  onRest(rest: Rest): number {  // For Rest type
			    return rest.duration;
			  }
			
			  onConcat(concat: Concat): number {  // For Concat type
			    return concat.first.accept(this) + concat.second.accept(this);
			  }
			}
			```
		- Each class (i.e. `Note`, `Rest`, `Concat`) just needs to implement an `accept` wrapper over the visitor:
			```ts
			class Note implements Music {
			  // `accept` wrapper that calls the visitor's function
			  accept<R>(visitor: MusicVisitor<R>): R {
				return visitor.onNote(this);
			  }
			}
			
			class Rest implements Music {
			  accept<R>(visitor: MusicVisitor<R>): R {
				return visitor.onRest(this);
			  }
			}
			
			class Concat implements Music {
			  accept<R>(visitor: MusicVisitor<R>): R {
				return visitor.onConcat(this);
			  }
			}
			```
		- At runtime, to actually call an instance of `Music`'s `duration` function, invoke the wrapper with the `DurationVisitor`:
			```ts
			const duration = music.accept(new DurationVisitor());
			```
		- This is much less common, but makes adding new operations to all `Music` subclasses very easy
			- You don't need to modify `Note`, `Rest`, `Concat` subclasses at all; just need to write a single new `xxxVisitor` class
		- Downside: if you add a new variant/subclass of `Music`, all `Visitor` classes must add a new `onXXX()` function


### Subclasses
- Automatically inherit methods of superclass + private representation
- Subclass spec is stronger than superclass
- DANGER: rep-exposure/dependence between sub/super classes
- Variables can have separate *static* and *dynamic types* (dynamic type must be subclass of static type)
	- *dynamic type*: type of object at runtime; only applies to the object itself, NOT the variable
	- *static type*: type that variable is declared with; only applies to the variable, NOT the object the variable points to itself
	- *Dynamic Dispatch*: How TypeScript determines which implementation of a method to use; picks the implementation of the *dynamic type*
		- i.e.:
		```ts
		const obj: Object = new FastMyString("hello");
		obj.toString() → ?  // This will use FastMyString's toString implementation since FastMyString is the dynamic type (Object) is the static type
		```
		- NOTE: static checking uses object's static type
			- i.e. `obj.charAt(0)` would not compile, since `obj`'s static type is `Object` which doesn't have `charAt()` func.

### Abstract Data Types
- **==Abstraction==.** Hiding low-level details with a simpler, higher-level idea.
- **==Information hiding==.** Hiding details of a module’s implementation from the rest of the system; those details can be changed later w/out changing the rest of the system.
- **==Encapsulation==.** Building a wall around a module so that the module is responsible for its own internal behavior, and bugs in other parts of the system can’t damage its integrity.
- **==Separation of concerns==.** Making a feature (or “concern”) the responsibility of a single module, rather than spreading it across multiple modules.
- Core idea: a type is characterized by its **abstraction***: its operations/functions/public interface. 
	- ***representation***: actual internal data structure + attributes
	- Classes of Operations:
		- *Creators*: create new objects of the type.
		- *Producers*: create new objects of the type, but require one or more existing objects of the type as input.
			- Note: comparison functions (i.e. `x.equals(y)`) are valid producers/operators
		- *Observers*: takes object of the type, returns objects of a different type.
		- *Mutators*: change objects. (ONLY APPLIES TO MUTABLE TYPES)
	- Example: Array (mutable)
		- creators: `Array` constructor, `[ _item1_, _item2_, _etc._ ]` literal syntax, [`Array.of`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Array/of), [`Array.from`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Array/from)
		- producers: [`Array.concat`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Array/concat), slicing
		- observers: `length`, `[..]` indexing syntax
		- mutators: `push`, `pop`, `shift`, `unshift`, [`reverse`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Array/reverse), [`sort`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Array/sort)
	- Good Practice:
		- simple, few operations
		- ***representation independent***
	- Testing: just need to test all its operations.
		- NEVER partition on internal representation details
		- Partition on how this instance was constructed
		- Partition on public-facing properties of the class that are expressible through public spec (i.e. via observers)
	- Good practices: `private` + `readonly`
	- CAREFUL: if returning references to mutable attributes, then clients could modify that attribute
		- ***Instead, use defensive copying in constructor (if taking in a mutable reference) and when returning the value of an attribute in any helper func.***
- **Abstraction Functions** & **Rep Invariants**
	- Abstract value space = set of values that the abstract type is designed to support
	- Representation value space = set of objects that actually implement the abstract values (based on chosen implementation)
	- Rules:
		- every abstract value has some rep value mapping to it (i.e. has a representation)
		- multiple rep values can map to the same abstract value
		- not all rep values map to an abstract value
	- Example: Abstract Value Space = Sets of chars. Representation Value Space = Strings
							<center><img src="School Supplements/6.102_abstraction_rep_values.png" alt="" style="width:350px; margin-top: 10px"/></center>

		- It's possible to have strings that are illegal for the give abstract type
	- ***Abstraction Function***: maps rep value to abstract value
		- There are many possible abstraction function maps + rep invariants -- the user must design this
	- ***Rep Invariant***: maps rep values to boolean (True/False maps to an abstract value)
		- NOTE: good practice to assert rep invariants at the end of every op that mutates the rep (or at the end of literally every function for defensive programming)
	- Both should be documented in code next to the representation itself, along w/justification of why the rep is safe from exposure to clients:
	```ts
	class CharSet {
	    private s: string;
	    // Rep invariant:
	    //   s contains no repeated characters
	    // Abstraction function:
	    //   AF(s) = {s[i] | 0 <= i < s.length}
	    //   NOTE: ALWAYS USE ACTUAL FUNCTION NOTATION HERE
	    //
	    // Safety from rep exposure:
	    //   All fields are private;
	    //   author and text are Strings, so are guaranteed immutable;
	    //   timestamp is a mutable Date, so Post() constructor and getTimestamp()
	    //        make defensive copies to avoid sharing the rep's Date object with clients.
	}
	```
	- Generally, in the justification of *Safety from rep exposure*, justify that types are either private/immutable or mutable but either is never returned/exposed to the client or is always returned with defensive copying
	- ***Benevolent Side Effects***: If the representation of an immutable object changes (but its abstract value doesn't change)
- Proving invariants about your datatype (using *structural induction*)
	1. established by creators and producers
	2. preserved by mutators, observers, and producers
	3. no rep exposure occurs
- MUTABLE REPS
	- If a mutable object is used as part of an abstract type's rep, there is danger of rep exposure since client maintains reference to that object and can modify it later.
		- BEST PRACTICE: make a copy of the mutable type after it's passed in by client. Then throw away the client's copy

### Recursive Data Types
```ts
BinaryTree<Element> = Empty + Node(e: Element, left: BinaryTree<Element>, right: BinaryTree<Element>)
```
- This is the formal defn. of the data type:
	- **abstract data type** on the left, defined by its **representation** (**concrete data type**) on the right
	- representation consists of **variants** of the data type combined by a union operator (`+`)
	- each variant is a class name with zero or more fields, written with name and type separated by a colon (`:`)
- ALWAYS WRITE A FORMAL DEFN. IN A COMMENT AT THE TOP OF A RECURSIVE DATA TYPE CLASS
- Every recursive data type must have a base case (i.e. `Empty`)
	- You can't have every element in the representation require a recursion
*Composite* Design Pattern:
- The idea of having an ADT contain instances of the other ADTs that implement the same interface (i.e. a `Song` contains many `Notes`)
- All can be operated on in the same way (i.e. `Song.play()` and `Note.play()` both work)
- Most recursive Data Types are Composite Patterns
Functions of Recursive Data Types
- are often recursive
- i.e. `contains(BinaryTree(e: Element, left: BinaryTree, right: BinaryTree), x: Element) = (e=x) or contains(left, x) or contains(right, x)`

NOTE: NEVER USE `instanceof` -- does dynamic type checking; bug-prone, not ready for change (if dynamic type changes but static type doesn't)

## Function Specs
- *Signature* (name, params, returns)
	- NOTE: do NOT include types here (or repeated info in the actual func. signature)
- *requires*: describe additional restrictions on params
- *effects*: describe return val, exceptions. Any mutation of inputs MUST be stated.
- *Precondition*: responsibility of the client -- satisfy function's *requires* and input types
- *Postcondition*: responsibility of the implementor -- function should satisfy its *effects* and return types **(conditioned on *precondition* being satisfied)**
- NOTE: func. signature is both part of precondition and postcondition
- Make implementation invisible in the spec
- Best to fail fast for inputs not satisfying the spec. For library/widely used funcs, use few preconditions but throw exceptions for invalid inputs
- **Deterministic** Specs (vs "underdetermined"): Outcome entirely determined by input (when satisfying precondition)
- **Declarative** Specs (vs Operational): 
	- Operational: series of steps function performs (i.e. pseudocode)
	- Declarative: only properties of outcome (***PREFERRED*** -- usually shorter, easier to understand, don't inadvertently suggest implementation details that clients may rely on when they aren't part of the actual spec)
- **Strength**: S2 *stronger* than S1 if implementations satisfying S2 all satisfy S1
	- *Stronger Precondition* = fewer valid inputs
	- *Stronger Postcondition* = fewer valid outcomes
	- S2 stronger than S1 iff S2's precondition weaker (same or more allowed inputs), S2's postcondition stronger *for inputs satisfying S1's precondition* (fewer allowed outcomes)
	- NOTE: when updating a function, you can weaken precondition or strengthen post-condition w/out affecting clients
	- NOTE: S1, S2 can also be *incomparable* if conflicting desired behavior on same valid input

## Static Checking
- Compile-time checking
- TS is static-checked, *not* dynamically checked (no runtime errors -- only "undefined" values)
- Mutation:
	- immutable = value cannot be changed
		- specific to the type (i.e. Strings are immutable; when you modify a string variable, you re-assign it)
	- constant = variable cannot be re-assigned
		- `const n: number = 5
		- Arrays often defined `const` if you never re-assign the array (you can still push/splice/mutate it)

## Testing
- *Validation*: process of uncovering problems in a program
	- *Verification*: formal reasoning/proof that program is correct
	- Code Review
	- Testing: running on selected inputs, checking results
- ALL TESTS MUST FOLLOW FUNC. SPEC.
- Test-First Programming:
	1. Write spec (func. signature, comments)
	2. Test/write test clients
	3. Implement (anything in function body)
- Systematic Testing:
	- *Correct*: accepts any legal implementation of the spec
	- *Thorough*: find bugs
	- *Small*
- Partition the input space
	- Include boundary conditions as separate measure zero partition
	- Problem: exponential blowup of # testcases with # parameters (if you handle all boundary cases for each parameter)
		- i.e.: 36 test cases for 2 inputs:
			<center><img src="School Supplements/6.1020_partition.png" alt="" style="width:300px; margin-top: 10px"/></center>
		- Solution: multiple partitions. Partition `a`, `b` separately; only require test cases in each subdomain independently rather than in every combination
		- Also introduce 3rd partition for interaction btwn `a`, `b` to ensure coverage of their interaction
						<center><img src="School Supplements/6.1020_triple_partition.png" alt="" style="width:300px; margin-top: 10px"/></center>
- *Blackbox Testing*: Test cases without knowledge of implementation
- *Glassbox Testing*; Test cases with knowledge of implementation, specifically to test edge cases based on implementation
- Coverage
	- *Statement Coverage*: every statement run by at least one test case
	- *Branch Coverage*: every control branch run
	- *Path Coverage*: every possible combination of branches run
	- Practically: shoot for *statement coverage*
- *Regression Test* case: when you find and fix bug, add it to test suite; prevents re-introducing the bug later
- *Fuzz Testing*: random inputs, verify no crashes
- *Property Testing*: random inputs, verify results satisfy some *property* (weaker than the function's desired output property)
