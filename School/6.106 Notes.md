## Assembly
Linux x86/64 Calling Convention
- Stack grows *down*, heap grows *up*
	- Literally, in address space
			<center><img src="School Supplements/6.106_stack_heap.png" alt="" style="width:200px; margin-top: 10px"/></center>
- Stack variables: func. args, return address, register state (i.e. saved register values to obey caller/callee-saved convention), local variables that don't fit in registers
- Stack is organized into frames; each function gets own frame
	 - `%rbp`: base pointer	
		- points to *top* of current stack frame
		- stationary
	- `%rsp`: stack pointer
		- points to *bottom* of current stack frame
		- grows downward as function puts more things on the stack
	- `%rip`: instruction pointer
		- `call` instruction saves `%rip` onto stack (to save where instruction ptr was prior to the func. call) and then jumps to the func.
		- `ret` instruction pops `%rip` from stack, jumps to `%rip`
	- Maintaining registers across calls
		- Caller responsible for saving some register state to stack (and restoring after the callee is finished) in case callee tries to use them; callee responsible for saving (and restoring, at the end of the function call) some other register states 
				<center><img src="School Supplements/6.106_register_table.png" alt="" style="width:500px; margin-top: 10px"/></center>
	- General Structure of a Function:
			<center><img src="School Supplements/6.106_function_structure.png" alt="" style="width:200px; margin-top: 10px"/></center>
		1. Store current base pointer (representing the anchor of the caller's stack frame)
		2. Set base pointer equal to stack pointer (setting the top/anchor of the new stack frame)
		3. Save callee-saved registers that the function will use
		4. Store args from caller
		5. Build any local variables/do function logic
		6. If calling another function:
			- Store args for callee
			- jump
		7. If returning:
			- Restore callee-saved registers
			- Restore base pointer
			- `retq`
- Deep Dive [Example](https://godbolt.org/z/xKhj73bdK):
	<center><img src="School Supplements/6.106_fibonacci_godbolt_example.png" alt="" style="width:500px; margin-top: 10px"/></center>
	- Linkage Block (from caller to current func.):
		- `pushq %rbp`: push current value of base pointer to stack (and decrement the stack pointer automatically)
		- `movq %rsp, %rbp`: Set base pointer equal to stack pointer
		- `pushq %rb14`, `pushq %rbx`: just saving values according to callee-saved convention (since the callee tries to use these registers)
		- `movq %rdi, %rbx`: saving value of `%rdi` to `%rbx`, since we need to free `%rdi` for when we do another func. call (`%rdi` is the designated register for the 1st arg. to a func. call)
	- If Statement:
		- `cmpq $2, %rdi`: compare `%rdi` (which holds `n`) to `2`; store result in RFLAG
		- `jl .LBB0_2`: jump to `LBB0_2` if comparison resulted in "less than"
	- Calls to `fib(n-1)` and `fib(n-2)`: 
		- Use either `leaq` or `addq` to compute `n-1` and `n-2`; store in `%rbx`
			- <sup>(`leaq` = "load effective address"; frequently abused to perform arithmetic but using a different part of the CPU than the ALU)</sup>
		- Move `%rbx` to `%rdi` (the register for 1st argument)
		- Then call `fib`
		- Store return value from `rax` to `rbx`
	- Function Postcursor:
		- `popq rb14`, `popq %rbx`: restore callee-saved register values
		- `popq %rbp`: pop base pointer value to where it was before this func. call
		- `retq`

## Multicore
Cache Coherence
- Processors use shared memory
- Each processor has its own cache
- Problem 1: memory is slow; inefficient for multiple processes to read from shared memory. Instead, it's faster for processors to share their cache data among each other
	- GOAL: give the illusion of shared memory, but actually share data between processes' caches
- Problem 2: If process x writes data to shared memory, then the cached value of that data in other processors' caches will become out of date
MSI Protocol
- Each cache line given a state:
	- **M**: cache block modified; all other caches must invalidate this line
	- **S**: other caches may be sharing this block
	- **I**: cache block invalid
- Example (4 caches/processors):

- Whenever you modify a cache line, you have to *invalidate* that line in all other caches

			- Example: adding 8 floats w/ 3 views. Cilk spawns 2 new identities, and cilk builds onto each identity before merging the 3 views
					<center><img src="School Supplements/6.106_cilk_reducer_example.png" alt="" style="width:450px; margin-top: 10px"/></center>	
				- (Cilk chooses the number of views/degree of parallelization)
			- Fun Facts:
				- Does not use mutex locks
				- Reducer/views implemented as hash-table; low-overhead
		- How to use:
			1. Define identity element func.
			2. Define merge step func.
			3. Define your reducer type and create an instance of it
			4. Treat your reducer exactly like what its view type is (access its fields, etc.)
		- Example (parallel summation):
		```C			
				// Set the reducer to zero, the identity element
				// NOTE: all cilk reducer functions require void* params, which you cast to the right type
				void zero_long(void* view) {
					*(long*)view = 0;
				}
				// left += right, the merge step
				void add_long(void* left, void* right) {
					*(long*)left += *(long*)right;
				}
				
				// Define new cilk_reducer type whose view is a `long`
				typedef long cilk_reducer(zero_long, add_long) LongReducer;
				LongReducer sum;
		
				...
				
				// ACTUAL USAGE OF REDUCER:
				cilk_for (int i = 0; i < N; i++) {
					sum += A[i];
				}
		```
		- NOTE: never pass a reducers to functions. Passing by value is disallowed. And passing by pointer will only retrieve a pointer to the local view of the reducer, not the reducer itself. In general, stick to global reducer variables

### Bounds on Parallelism
Trace DAG
- Vertices are strands -- sequence of instructions not containing a spawn or sync
- Edges are call sequences (spawns, call, return, or continue)
	<center><img src="School Supplements/6.106_fib(4)_trace_DAG_with_code.png" alt="" style="width:475px; margin-top: 10px"/><img src="School Supplements/6.106_fib(4)_trace_DAG.png" alt="" style="width:475px; margin-top: 10px"/></center>
- `cilk` runtime converts `cilk_for` loops to `cilk_spawn` and `cilk_sync`s to then build a trace DAG
Parallelism as a unit of measure
- Define $T_p$ = execution time on $P$ processors
	- $T_1$ = total work (i.e. serial runtime)
	- $T_\infty$ = *span* -- length of longest path from $s$ to $t$ in trace DAG
		- You can't avoid running these traces serially due to serial dependencies
		- runtime is at least as long as the span
- *Speedup* = given # processors $P$, how much faster code will be
	- If $\frac{T_1}{T_P} = P$, perfect *linear* speedup (as opposed to sublinear or superlinear)
		- Almost impossible in practice due to overhead
- *Parallelism* = *maximum* speedup compared to serial code
	- = $\frac{T_1}{T_\infty}$   (work / span)
- *Amdahl's law*: if $\alpha$ frac. of application must be run serially, then speedup can be at most $\frac{1}{\alpha}$
	- Speedup $\le T_1 / T_p$
			 = $T_1 / (α T_1 + (1 - α) T_1 / P)$
		 - As $P$ $\rightarrow \infty$, Speedup = $\frac{1}{\alpha}$
- *Work Law*: $T_p \ge T_1 / P$
		- runtime on $P$ processors is at least the total work divided by number of processors
		- i.e. best case is dividing total work equally by all processors
- *Span Law*: $T_p \ge T_\infty$
	- You can't beat the *span*'s runtime
	- Speedup $\le \frac{T_1}{T_\infty} =$ *parallelism*
- Series Compositions
			<center><img src="School Supplements/6.106_series_composition.png" alt="" style="width:250px; margin-top: 10px"/></center>	
	- $T_1(A \cup B) = T_1(A) + T_a(B)$ -- total work = sum of individual work
	- $T_\infty(A \cup B) = T_\infty(A) + T_\infty(B)$ -- total span = sum of individual span
- Parallel Compositions
			<center><img src="School Supplements/6.106_parallel_composition.png" alt="" style="width:150px; margin-top: 10px"/></center>	
	- $T_1(A ∪ B) = T_1(A) + T_a(B)$
	- $T_\infty(A \cup B) = \max(T_\infty(A), T_\infty(B)$) -- total span = max of individual spans
- Example:
			<center><img src="School Supplements/6.106_example_trace_DAG.png" alt="" style="width:150px; margin-top: 10px"/></center>	
	- At least 3 strands are serial (out of 18) -- Amdahl's law states: <= 6x speedup
		<center><img src="School Supplements/6.106_example_trace_DAG_serial_traces.png" alt="" style="width:150px; margin-top: 10px"/></center>	
	- $T_1$ = total work (i.e. serial runtime) = 18 (18 nodes total)
	- $T_\infty$ = *span* -- length of longest path from $s$ to $t$ = 9:
			<center><img src="School Supplements/6.106_trace_DAG_span.png" alt="" style="width:150px; margin-top: 10px"/></center>	
	- Possible Parallelism:
		- Amdahl's Law: 18 / 3 = 6x speedup
		- Span Law: 18 / 9 = 2x speedup
- Span Law is usually the tightest; actually considers serial dependencies in computation
	- Amdahl's law good for general understanding (non-specific to a given program or known serial dependencies)
	- Both give valid upper bounds on speedup

### Scheduling Theory
Greedy Scheduling
- A strand is *ready* if all predecessors have executed
	- i.e. if Blue = executed, then Yellow = *ready*
		<center><img src="School Supplements/6.106_executed_vs_ready_trace_DAG.png" alt="" style="width:150px; margin-top: 10px"/></center>	
- Scheduler greedily puts any available strands onto every available processor
	- *Complete step*: If all processors are occupied; $P$ processors, $\ge P$ strands *ready*
	- *Incomplete step*: $<P$ strands *ready*, scheduler executes all of them, but some processors idle
	- KEY GOAL: minimize # incomplete steps
- Theorem: Any greedy scheduler achieves $T_p \le \frac{T_1}{P} + T_\infty$
	- Recall: Work law: $T_p \ge T_1 / P$
			Span law: $T_p \ge T_\infty$
	- **Sum of span and work law lower bounds is an upper bound on runtime of greedy scheduler**
	- This implies greedy scheduler is $\le2 \times$ optimal scheduler
	- If $\frac{T_1}{T_\infty} \gg P$  (i.e. parallelism much larger than # processors), approaching perfect linear speedup
		- There's almost always extra tasks to be scheduled
- *Parallel Slackness*: $\frac{T_1}{T_\infty} / {P}$   (parallelism divided by # processors)
	- Want this to be like 10x or more
	- Then almost all steps are complete steps
Cilk's Randomized Work-stealing scheduler:
- Achieves $T_p = \frac{T_1}{P} + O(T_\infty)$ (approximately 1x $T_\infty$ empirically) -- achieves roughly the greedy bound in practice
- `Cilkscale` allows you to measure work ($T_1$) and span ($T_\infty$) so you can check if $\frac{T_1}{T_\infty} \gg P$ and if you can expect ~linear speedup

### Parallel Loops
`Cilk` doesn't parallelize loops directly; compiles it into divide/conquer recursion of `cilk_spawn`'s
- Example (left gets compiled into the right): Matrix Transpose
		<center><img src="School Supplements/6.106_cilk_parallel_loop_example.png" alt="" style="width:550px; margin-top: 10px"/></center>	
	- Binary recursion tree to iterate through the loop
	- Original body of loop gets pasted as the base case of recursive function
	- Trace DAG:	
			<center><img src="School Supplements/6.106_matrix_transpose_cilk_for_trace_DAG.png" alt="" style="width:550px; margin-top: 10px"/></center>	
		- Iteration `i` of the `cilk_for` executes an inner loop with `i` iterations
		- Work $T_1$: $O(n^2)$
			- The serial code does $O(n^2)$ work; work is asymptotically equal regardless of parallel vs serial implementation
				- Parallel work analysis:
					- $O(n)$ leaf nodes, doing up to $O(n)$ work each -- equivalent to serial work
					- Each internal (non-leaf) node is constant work -- just spawning children/control flow
						- $n-1$ internal nodes total
					- Still $O(n^2)$ work total
		- Span $T_\infty$: $O(n + log ~n) = O(n)$
			- Longest path through the DAG highlighted in yellow -- proportional to height of DAG = $O(log ~n)$
			- The leaf node does $O(n)$ work
		- Parallelism: $\frac{T_1}{T_\infty} = \frac{O(n^2)}{O(n)} = O(n)$
- Example: Vector Addition
			<center><img src="School Supplements/6.106_cilk_parallel_loop_example_single_loop.png" alt="" style="width:550px; margin-top: 10px"/></center>	
	- Work $T_1$: $O(n)$
	- Span $T_\infty$: $O(log ~n)$
	- Parallelism: $\frac{T_1}{T_\infty} = O(\frac{n}{log ~n})$
Coarsening the recursion
- Compiler does do automatically; OR: force compiler using `#pragma cilk grainsize G` (ALMOST ALWAYS A BAD IDEA)
	- Cilk runtime coarsens recursion to try to get parallel slackness ~8-10
- With $G$ coarsened recursion:
		<center><img src="School Supplements/6.106_cilk_parallel_loop_example_single_loop_trace_DAG.png" alt="" style="width:550px; margin-top: 10px"/></center>	
	- Trace DAG has $\frac{n}{G}$ leaves
	- Define: $S$ = time for control flow to run (i.e. to compute `mid`, call `cilk_spawn`, `return`, etc.)
	- Define: $I$ = time for loop body to run (i.e. `A[i] += B[i]`)
	- Work: $T_1 = n·I + (n/G ~–~ 1)·S$   ($n \cdot I$ is constant, useful work from performing loop body; $n / (G - 1) \cdot S$ is $S$ overhead/control-flow work over $n / (G-1)$ internal nodes)
		- NOTICE: Larger $G$ reduces total work (reduces $(n/G ~–~ 1)·S$, the control loop overhead)
	- Span: $T_\infty = G · I + \log(n/G)·S$   ($G \cdot I$ is work of the leaf node which is coarsened $G$x; $\log(n / G) \cdot S$ is $S$ work over $\log(n / G)$ depth of the DAG)
		- Highlighted yellow
		- NOTICE: Smaller $G$ reduces total span (less work per leaf node)
	- Parallelism: $\frac{T_1}{T_\infty} = \frac{n·I + (n/G ~–~ 1)·S}{G · I + \log(n/G)·S}$
	- HOW TO PICK $G$:
		- Define *overhead fraction* $= \frac{\text{overhead/control-flow work}}{\text{useful work from loop body}} = \frac{n(G-1)S}{nI} = (\frac{n}{G} - 1) \frac{S}{nI} = (\frac{n - G}{G}) \frac{S}{nI} = \underbrace{(\frac{n-G}{n}) \frac{S}{GI} \approx \frac{S}{GI}}_{G \ll n \implies (\frac{n-G}{n}) \approx 1}$
		- Want to keep this below ~$10\% \rightarrow$ Pick $G$ s.t. $0.1 \ge \frac{S}{GI} \implies G \approx 10\frac{S}{I}$
- KEY TAKEAWAY: coarsening recursion trades off parallelism for lower total work (due to lower control loop overhead)
	- You only want as much parallelism as will keep your processors busy
Why simply spawning children iteratively isn't as good as binary divide and conquer spawning:
- Example: Vector Addition, spawning children iteratively
	<center><img src="School Supplements/6.106_cilk_parallel_loop_example_linear_parallelization.png" alt="" style="width:300px; margin-top: 10px"/></center>	
	- Work: $T_1 = n·I + (n/G ~–~ 1)·S$
	- Span: $T_\infty = G \cdot I + n/G \cdot S$    (longest path highlighted in yellow)
	- Parallelism:  $\frac{T_1}{T_\infty} = \frac{n·I + (n/G ~–~ 1)·S}{G · I + n/G·S}$  compared to  $\frac{n·I + (n/G ~–~ 1)·S}{G · I + \log(n/G)·S}$ from divide and conquer approach
		- Smaller parallelism
		- Intuition: spawn chain is a long series chain instead of a balanced tree; span is much longer.
			- This makes a difference if $S$ is reasonably large compared to $I$ to matter
Practical Tips:
- Minimize span to maximize parallelism
- Try to generate ~10x parallelism
- If you have tons of parallelism, trade if off to reduce work overhead
- Avoid spawning in a loop; use `cilk_for` or use divide-and-conquer
- Parallelize outer loops instead of inner loops (so each chunk is larger)

## Vectorization
SIMD: single instruction multiple data -- integrated in hardware
- New instruction set + new
- set of registers
- Most recent innovations in computer architecture touch these new added instructions/registers

Vector Instructions (Intrinsics)
- [Intel Intrinsics Guide](https://www.intel.com/content/www/us/en/docs/intrinsics-guide/index.html#techs=AVX_512)
- Naming (when invoked in C): `_mm<vec-width>_<op>_<scalar-type>`
		<center><img src="School Supplements/6.106_multimedia_instruction_naming.png" alt="" style="width:450px; margin-top: 10px"/></center>	
	- Note on scalar-type: 
		- "epi" = "extended packet" + "int"
		- "ps" = "packed single-precision (32-bit float)"
		- "pd" = "packed double-precision (64-bit float)"
		- "si" = "packed int" (this is used often in AVX512)
- Important Instructions:
	- Arithmetic/Logic:
		- `__m512i _mm512_set1_epi64(double a)`: broadcast `a` to all lanes
		- `__m128i _mm_add_epi32(__m128i a, __m128i b)`: vectorized add
		- `__m256i _mm_mul_epi32(__256i a, __256i b)`: vectorized multiply; multiplies 4x 32-bit ints, produces 4 64-bit ints
			- IMPORTANT: interprets `a` and `b` as 8-lanes of 32-bit signed ints, but only uses values 0, 2, 4, 6:
				- `a = [a0, -, a2, -, a4, -, a6, -]`
				- `b = [b0, -, b2, -, b4, -, b6, -]`
				- interprets output as 4-lanes of 64-bit signed ints
			- This is because multiplication of ints usually produces much larger ints
	- Compare:
		- `__m128 _mm_cmp_ps(__m128 a, __m128 b, const int imm8)`: vectorized compare
			- `imm8` can take values from 0-31 mapping to different types of comparisons
			- `a`, `b` interpreted as 4x lane 32-bit floats
			- output is a 4x lane where each lane is either `0xFFFFFFFF` or `Ox00000000` if comparison is True or False
	- Loads/Store:
		- `__m256 _mm256_loadu_ps(float const * mem_addr)`: Loads 256 bits (as 8x consecutive 32-bit floats) from `mem_addr`
			- Returns the 8 floats packed in a `__m256` register
			- NOTE: the `u` at the end of `loadu` indicated "unaligned" write -- the address does not need to be a multiple of 32.
		- `void _mm256_storeu_ps(float *mem_addr, __m256 a)`: Writes 256 bits to `mem_addr` 
		- Stream writes: 
			- Normally, during a write, you need to first read the line from cache/memory, write the part you want to write, *then* write the whole line back into cache
			- Stream writes are applicable if you are overwriting an entire cache line; just skips the loading step and writes immediately. ~2x faster
	- Non-SIMD vector ops:
		- Shuffle: mix the lanes of the vector register
		- Unpack: expand the upper N lanes to take the space of the full vector
		- Dot Product: dot products between vectors
		- addsub: Add values from all even lanes; subtract values from all odd lanes
How to get the Compiler to Vectorize for you
- 2 types of vectorizers:
	- Loop vectorizer
	- Superword Level Parallelism (SLP) Vectorizer
- Loop Vectorization: 
	- If each iteration of loop can be run in parallel, then loop can be vectorized
	- "Reduction" can also be vectorized (i.e. cumulative sum of an array) even though instructions are not independent; compiler can usually implement partial sums per k-lanes, then sum k lanes results, etc. and apply a divide-and-conquer approach
- SLP Vectorization:
	- First, unroll the loop a bit (i.e. 8x)
	- Then, move every set of 8 identical operations next to each other (i.e. re-order operations)
	- Fuse those identical operations into vectorized op
- In practice...
	- **Vectorization highly compiler dependent -- Need to pay attention to ASM; may need to add vectorization manually**
Matrix Extensions
- Next step after vectorization
- Intel AMX
	- 8 new 1024 bits registers -- TMM0 - TMM7
	- Tile configuration -- configure the registers to be between 1 - 16 rows
	- Only a few Operations: Load/Store, Zero, Matrix Multiply
	- Basically made to accelerate matrix multiply
In Practice (looking at the ASM of a vectorized loop):
- You might see initially loop runs using ZMM vectors registers -- full vectorization
	- Then, when few loops remain, uses YMM (smaller) vector registers
	- And then, for stragglers, just uses non-vector ops
- Using `restrict` can allow much more compiler vectorization when operating on multiple pointers
	- Compiler needs to be assured that address ranges for each pointer don't overlap; if they do overlap, vectorization can produce wrong results compared to sequential computation.
	- Without `restrict`, compiler will add some overhead to check where the overlap region between the pointers is, and try to vectorize where possible, while using sequential computation if it's unsure that the pointer regions don't overlap.

**x86 Architecture**
- 3 core architectural ideas:
	- Parallelism (instruction-level parallelism, pipelining (having each stage of pipeline execute a different instruction at any given moment), multi-code)
	- Locality (use caching to save data that's been recently used, hoping that it'll be used again)
	- Branch Prediction (predict branches and run in advance)
- Pipelining & Dealing w/ Stalls
	- Functional Units
		- Different instructions (i.e. addition vs division) take different # cycles; cause stalls
		- Solution: instead of having a single ALU, split it into multiple "functional units" that can run at the same time
			- Each functional unit can also be pipelined, so it can run multiple instructions in parallel
		- The fetch and decode stages 
	- Branch Predictors
		- Maintain table mapping addresses of branch instructions to predictions of their outcome
	- Dealing with Data Dependencies:
		- 3 types of data dependencies:
			- RAW (Read after Write): Must wait for write to finish before read
			- WAR (Write after Read):  Usually name-dependencies if multiple independent instructions use same register name
			- WAW (Write after Write): Usually name-dependencies if multiple independent instructions use same register name
		- Bypassing:
			- If instruction 2 reads what instruction 1 writes:
							<center><img src="School Supplements/6.106_read_write_stall.png" alt="" style="width:175px; margin-top: 10px"/></center>	
				- This cases a stall until instruction 1 finishes writing to `%rax`
			- Bypassing: allows instruction 2 to read the result of instruction 1 before it's been written to `%rax`
				<center><img src="School Supplements/6.106_bypassing.png" alt="" style="width:450px; margin-top: 10px"/></center>	
		- Register Renaming: Fixes WAW + WAR dependencies by changing which register you're using
			- Intel Haswell has only 16 registers accessible in code, but they map to 168 physical registers to avoid dependencies
		- Out-of-order Execution: Reduces impact of RAW dependencies
			- While Read is waiting for Write to finish, CPU can execute other, independent instructions in the meantime
	- SMT: simultaneous multi-threading
		- 2 instruction streams running at the same time; if one stalls, switch to running the other

## Bentley Rules
**4 Categories of Optimization for reducing "Work"**
Data Structures
- *Packing*: store >1 data value in 1 machine word
```C
	typedef struct {
		int year: 13;  // 13-bit field
		int month: 4;
		int dat: 5;
	} date_t;
```
- *Encoding*: convert data into form that requires fewer bits
- *Augmentation*: add extra info to data structure to make common ops faster
	- i.e. adding both head/tail ptrs to linked list if doing lots of list concat
- *Caching*: avoid unnecessary recomputation
- *Precomputation*: calculate + store lookup table ahead of time to avoid doing them at "test-time"
- *Compile-time Initialization*: Same as pre-computation, but at compile-time (i.e. just hard-coding values)
	- Metaprogramming: Writing program whose output is source code (or i.e. code for a large lookup table) that you paste into your actual program
	- Multi-stage Programming: 
		- `static_var<type>` are evaluated in stage 1 and replaced w/ compiled values
		- `dyanmic_var<type>` are evaluated in stage 2 (using stored `static_var<type>` values)
		- i.e. (left: pre-stage 1, right: post-stage 1 -- notice how `setup()` gets compiled into constants)
			<center><img src="School Supplements/6.106_multistage_program.png" alt="" style="width:600px; margin-top: 10px"/></center>	
- *Sparsity*: Avoid storing and computing with 0's
	- Compressed Sparse Rows (CSR)
			<center><img src="School Supplements/6.106_sparsity.png" alt="" style="width:400px; margin-top: 10px"/></center>	
		- `rows`: each index corresponds to a row; value indicates start of a slice into `cols`
		- `cols`: parallel list w/ `vals`; specifies the column that each val goes in (in given row) 
		- `vals`: parallel list w/ `cols`; specifies val (in given column + row)
		- Storage $O(n + nnz)$
		- mat-vec-mul $O(nnz)$
				<center><img src="School Supplements/6.106_sparse_mat_vec_mul.png" alt="" style="width:400px; margin-top: 10px"/></center>	
Logic
- *Constant Folding & Propagation*: during compilation, eval constant expressions, substitute results into code (usually done by compiler)
- *Common Sub-expression Elimination*: avoid computing same expression multiple times; instead, cache and substitute (usually somewhat done by compiler)
- *Algebraic Identities*: simplify algebraic formulas
- *Create a Fast Path*: run a quick check first (that passes most of the time) before running complete, thorough check (if the first check fails)
- *Short-Circuiting*: stop/break as soon as you know the answer
- *Ordering Tests*: run tests first that are more likely to allow breaking/stopping before running other tests
	- i.e. Skydio's sample selection
- *Combining Tests*: replace branching/casework (incurs overhead) with computation + lookup array or a switch statement
Loops
- *Loop Unrolling*: unroll multiple iterations of loop into a single iteration
	- avoid overhead from branching/control
	- allow compiler to do more optimization within a single iteration
- *Hoisting / Loop-Invariance Code Motion*: move loop-invariant code (i.e. code that generates the same result every iter of the loop) outside of the loop
- *Loop Fusion / Jamming*: if you have multiple loops over same indices, combine them into 1 loop
Functions
- Functions incur branching/control overhead
- *Inlining*: Don't use function; just inline its body
	- Reduces control flow overhead + allows compiler to do more optimization
	- The compiler does this for you using `inline void func(...)` keyword
	- Basically always good, unless this induces massive code size blowup (i.e. if the function is called in a loop w/tons of iters)
- *Tail-Recursion Elimination*: If the last call in a function is a recursive self-call, avoid the self-call by simply branching back to the top of the function
- *Coarsening Recursion*: Increase size of the base-case to reduce amount of recursion
	- i.e. for small inputs, use non-recursive, faster special case to solve. Only call recursion for large inputs

- Swapping 2 variables
	- `x = x ^ y`
	- `y = x ^ y`
	- `x = x ^ y`
	- Why this works: `XOR` is its own inverse: `(x ^ y) ^ y = x`

- Min of 2 ints
	- Simple method: `r = (x < y) ? x : y`
	- `r = y ^ ((x ^ y) & -(x < y))`
		- `(x < y)` returns all 1 if `x < y`, else 0. Then, the minus sign turns this into all 1's (an all-1 mask) or all 0's.
		- if `x < y`:
			- `r = y ^ (x ^ y) = x`
		- if `x > y`:
			- `r = y ^ ((x ^ y) & 0) = y`

## Review
- Intuition of subtracting 1:
	- `10110000` --> `10101111`
	- essentially remove the last 1, then replace all the trailing 0's with 1's
- 2's complement:
	- Leading 1 is negative valued; all other digits positive valued
	- To find 2's complement representation, this is a simple trick: `-x = ~x + 1`
		1. Represent `+x` in binary
		2. Flip all the bits
		3. Add 1
	- i.e.: to represent -28:
		- +28 in binary: `00011100`
		- ~28: `11100011`
		- ~28 + 1: `11100100`   <--   -28 in binary
- Speculative branch prediction
	- Keeps history of running this branch in the past -- repeats most common from history
	- Note: branch mis-prediction is costly -- on order of an L2 cache miss
