## Vectorization
SIMD: single instruction multiple data -- integrated in hardware
- New instruction set + new set of registers
- Most recent innovations in computer architecture touch these new added instructions/registers
k-Wide Vector Unit
- Vector Register holds k words
- ALU has k lanes; all lanes operate in *lock-step*; use same instruction/control signals (k=4 in this image)
		<center><img src="School Supplements/6.106_multi-lane_registers_and_ALUs.png" alt="" style="width:450px; margin-top: 10px"/></center>	
- In ops that involve multiple vector registers, vectors interact element-wise; i.e. element i in vector 1 only interacts with element i in vector 2
- Naming convention:
	- XMM, YMM, ZMM alias to different parts of same vector registers
			<center><img src="School Supplements/6.106_vector_register_aliasing.png" alt="" style="width:450px; margin-top: 10px"/></center>	
- Every vector register can have different data types (which result in different variable names when referenced in C code)
		<center><img src="School Supplements/6.106_vector_register_data_types.png" alt="" style="width:675px; margin-top: 10px"/></center>	
	- Other common types:
		- `__mm256i`: 256-bit vector if ints (can be 8 x 32-bit ints, 16 x 16-bit ints, 32 x 8-bit ints, etc., depending on usage)
Vector Instructions (Intrinsics)
- [Intel Intrinsics Guide](https://www.intel.com/content/www/us/en/docs/intrinsics-guide/index.html#techs=AVX_512)
- Naming (when invoked in C): `_mm<vec-width>_<op>_<scalar-ty>`
		<center><img src="School Supplements/6.106_multimedia_instruction_naming.png" alt="" style="width:450px; margin-top: 10px"/></center>	
	- Note: "mm" = "multi-media" (legacy naming artifact -- vectorization used to be used for video/audio)
- Important Instructions:
	- Arithmetic/Logic:
		- `__m128i _mm_add_epi32(__m128i a, __m128i b)`: vectorized add
		- `__m256i _mm_mul_epi32(__256i a, __256i b)`: vectorized multiply; multiplies 4x 32-bit ints, produces 4 64-bit ints
			- IMPORTANT: interprets `a` and `b` as 8-lanes of 32-bit signed ints, but only uses values 0, 2, 4, 6:
				- `a = [a0, -, a2, -, a4, -, a6, -]`
				- `b = [b0, -, b2, -, b4, -, b6, -]`
				- interprets output as 4-lanes of 64-bit signed ints
			- This is because multiplication of ints usually produces much larger ints
	- Compare:
		- `__m128 _mm_cmp_ps(__m128 a, __m128 b, const int imm8)`: vectorized compare
			- `imm8` can take values from 0-31 mapping to different types of comparisons
			- `a`, `b` interpreted as 4x lane 32-bit floats
			- output is a 4x lane where each lane is either `0xFFFFFFFF` or `Ox00000000` if comparison is True or False
	- Loads/Store:
		- `__m256 _mm256_loadu_ps(float const * mem_addr)`: Loads 256 bits (as 8x consecutive 32-bit floats) from `mem_addr`
			- Returns the 8 floats packed in a `__m256` register
			- NOTE: the `u` at the end of `loadu` indicated "unaligned" write -- the address does not need to be a multiple of 32.
		- `void _mm256_storeu_ps(float *mem_addr, __m256 a)`: Writes 256 bits to `mem_addr` 
		- Stream writes: 
			- Normally, during a write, you need to first read the line from cache/memory, write the part you want to write, *then* write the whole line back into cache
			- Stream writes are applicable if you are overwriting an entire cache line; just skips the loading step and writes immediately. ~2x faster
	- Non-SIMD vector ops:
		- Shuffle: mix the lanes of the vector register
		- Unpack: expand the upper N lanes to take the space of the full vector
		- Dot Product: dot products between vectors
		- addsub: Add values from all even lanes; subtract values from all odd lanes
How to get the Compiler to Vectorize for you
- 2 types of vectorizers:
	- Loop vectorizer
	- Superword Level Parallelism (SLP) Vectorizer
- Loop Vectorization: If each iteration of loop can be run in parallel, then loop can be vectorized
- SLP Vectorization:
	- First, unroll the loop a bit (i.e. 8x)
	- Then, move every set of 8 identical operations next to each other
	- Fuse those identical operations into vectorized op
- In practice...
	- **Vectorization highly compiler dependent -- Need to pay attention to ASM; may need to add vectorization manually**
Matrix Extensions
- Next step after vectorization
- Intel AMX
	- 8 new 1024 bits registers -- TMM0 - TMM7
	- Tile configuration -- configure the registers to be between 1 - 16 rows
	- Only a few Operations: Load/Store, Zero, Matrix Multiply
	- Basically made to accelerate matrix multiply
In Practice (looking at the ASM of a vectorized loop):
- You might see initially loop runs using ZMM vectors registers -- full vectorization
	- Then, when few loops remain, uses YMM (smaller) vector registers
	- And then, for stragglers, just uses non-vector ops
- Using `restrict` can allow much more compiler vectorization when operating on multiple pointers
	- Compiler needs to be assured that address ranges for each pointer don't overlap; if they do overlap, vectorization can produce wrong results compared to sequential computation.
	- Without `restrict`, compiler will add some overhead to check where the overlap region between the pointers is, and try to vectorize where possible, while using sequential computation if it's unsure that the pointer regions don't overlap.

## Assembly & Computer Architecture
**Assuming fixed amount of "work"... how to make it run faster?**
4 Stages:
1. Pre-processing
	- Expand macros
	- Still C code... stored in `.i` files
2. Compiling
	- Convert C to ASM (`.s` files)
3. Assembling
	- Convert to `.o` object files
	- You can modify `.s` ASM files and "assemble" into `.o` files: `clang FILE.s –o FILE.o`
	- Also possible to "disassemble" -- turn `.o` back into ASM code for debugging/investigation
4. Linking
	- Merge all objects, libraries into 1 executable

**x86 Architecture**
- 3 core architectural ideas:
	- Parallelism (instruction-level parallelism, pipelining (having each stage of pipeline execute a different instruction at any given moment), multi-code)
	- Locality (use caching to save data that's been recently used, hoping that it'll be used again)
	- Branch Prediction (predict branches and run in advance)
- Pipelining & Dealing w/ Stalls
	- Functional Units
		- Different instructions (i.e. addition vs division) take different # cycles; cause stalls
		- Solution: instead of having a single ALU, split it into multiple "functional units" that can run at the same time
			- Each functional unit can also be pipelined, so it can run multiple instructions in parallel
		- The fetch and decode stages 
	- Branch Predictors
		- Maintain table mapping addresses of branch instructions to predictions of their outcome
	- Dealing with Data Dependencies:
		- 3 types of data dependencies:
			- RAW (Read after Write): Must wait for write to finish before read
			- WAR (Write after Read):  Usually name-dependencies if multiple independent instructions use same register name
			- WAW (Write after Write): Usually name-dependencies if multiple independent instructions use same register name
		- Bypassing:
			- If instruction 2 reads what instruction 1 writes:
							<center><img src="School Supplements/6.106_read_write_stall.png" alt="" style="width:175px; margin-top: 10px"/></center>	
				- This cases a stall until instruction 1 finishes writing to `%rax`
			- Bypassing: allows instruction 2 to read the result of instruction 1 before it's been written to `%rax`
				<center><img src="School Supplements/6.106_bypassing.png" alt="" style="width:450px; margin-top: 10px"/></center>	
		- Register Renaming: Fixes WAW + WAR dependencies by changing which register you're using
			- Intel Haswell has only 16 registers accessible in code, but they map to 168 physical registers to avoid dependencies
		- Out-of-order Execution: Reduces impact of RAW dependencies
			- While Read is waiting for Write to finish, CPU can execute other, independent instructions in the meantime
	- SMT: simultaneous multi-threading
		- 2 instruction streams running at the same time; if one stalls, switch to running the other

## Bentley Rules
**4 Categories of Optimization for reducing "Work"**
Data Structures
- *Packing*: store >1 data value in 1 machine word
```C
	typedef struct {
		int year: 13;  // 13-bit field
		int month: 4;
		int dat: 5;
	} date_t;
```
- *Encoding*: convert data into form that requires fewer bits
- *Augmentation*: add extra info to data structure to make common ops faster
	- i.e. adding both head/tail ptrs to linked list if doing lots of list concat
- *Caching*: avoid unnecessary recomputation
- *Precomputation*: calculate + store lookup table ahead of time to avoid doing them at "test-time"
- *Compile-time Initialization*: Same as pre-computation, but at compile-time (i.e. just hard-coding values)
	- Metaprogramming: Writing program whose output is source code (or i.e. code for a large lookup table) that you paste into your actual program
	- Multi-stage Programming: 
		- `static_var<type>` are evaluated in stage 1 and replaced w/ compiled values
		- `dyanmic_var<type>` are evaluated in stage 2 (using stored `static_var<type>` values)
		- i.e. (left: pre-stage 1, right: post-stage 1 -- notice how `setup()` gets compiled into constants)
			<center><img src="School Supplements/6.106_multistage_program.png" alt="" style="width:600px; margin-top: 10px"/></center>	
- *Sparsity*: Avoid storing and computing with 0's
	- Compressed Sparse Rows (CSR)
			<center><img src="School Supplements/6.106_sparsity.png" alt="" style="width:400px; margin-top: 10px"/></center>	
		- `rows`: each index corresponds to a row; value indicates start of a slice into `cols`
		- `cols`: parallel list w/ `vals`; specifies the column that each val goes in (in given row) 
		- `vals`: parallel list w/ `cols`; specifies val (in given column + row)
		- Storage $O(n + nnz)$
		- mat-vec-mul $O(nnz)$
				<center><img src="School Supplements/6.106_sparse_mat_vec_mul.png" alt="" style="width:400px; margin-top: 10px"/></center>	
Logic
- *Constant Folding & Propagation*: during compilation, eval constant expressions, substitute results into code (usually done by compiler)
- *Common Sub-expression Elimination*: avoid computing same expression multiple times; instead, cache and substitute (usually somewhat done by compiler)
- *Algebraic Identities*: simplify algebraic formulas
- *Create a Fast Path*: run a quick check first (that passes most of the time) before running complete, thorough check (if the first check fails)
- *Short-Circuiting*: stop/break as soon as you know the answer
- *Ordering Tests*: run tests first that are more likely to allow breaking/stopping before running other tests
	- i.e. Skydio's sample selection
- *Combining Tests*: replace branching/casework (incurs overhead) with computation + lookup array or a switch statement
Loops
- *Loop Unrolling*: unroll multiple iterations of loop into a single iteration
	- avoid overhead from branching/control
	- allow compiler to do more optimization within a single iteration
- *Hoisting / Loop-Invariance Code Motion*: move loop-invariant code (i.e. code that generates the same result every iter of the loop) outside of the loop
- *Loop Fusion / Jamming*: if you have multiple loops over same indices, combine them into 1 loop
Functions
- Functions incur branching/control overhead
- *Inlining*: Don't use function; just inline its body
	- Reduces control flow overhead + allows compiler to do more optimization
	- The compiler does this for you using `inline void func(...)` keyword
	- Basically always good, unless this induces massive code size blowup (i.e. if the function is called in a loop w/tons of iters)
- *Tail-Recursion Elimination*: If the last call in a function is a recursive self-call, avoid the self-call by simply branching back to the top of the function
- *Coarsening Recursion*: Increase size of the base-case to reduce amount of recursion
	- i.e. for small inputs, use non-recursive, faster special case to solve. Only call recursion for large inputs


## C Tricks
- NOTE: good practice to always use `unsigned` types if doing bit hacks
- Get an all 1's mask: `-1` (recall 2's complement representation of negative numbers)
- Set k<sup>th</sup> bit: `x | (1 << k)`
- Clear k<sup>th</sup> bit: `x & ~(1 << k)`
- Toggle the k<sup>th</sup> bit: `x ^ (1 << k)`
- Extract a bit field: `(x & mask) >> shift`
	- (`mask` indicates the bit field to be extracted, `shift` shifts this bit field in the LSB)
		<center><img src="School Supplements/6.106_extract_bit_field.png" alt="" style="width:400px; margin-top: 10px"/></center>	
- Set a bit field: `(x & ~mask) | (y << shift)`
	- (`mask` indicates the bit field, `y` is the value to set it to)
				<center><img src="School Supplements/6.106_set_bit_field.png" alt="" style="width:525px; margin-top: 10px"/></center>	
	- Safer version: `(x & ~mask) | ((y << shift) & mask)`
		- (Mask `y` before ORing with `x` to prevent flipping incorrect bits (highlighted pink))
						<center><img src="School Supplements/6.106_set_bit_field_safe.png" alt="" style="width:525px; margin-top: 10px"/></center>	
- Circular Buffer (more like a modulo $2^k$): 
	- `mask = ((1 << k) - 1)`
	- `x = (x + 1) & mask`
	- This is much more efficient than a `%` operator					<center><img src="School Supplements/6.106_circular_buffer.png" alt="" style="width:425px; margin-top: 10px"/></center>	
- Mask for Least-significant 1
	- `mask = x & (-x)`
	- Why this works: `-x = ~x + 1` (2's complement representation of negative ints)
			<center><img src="School Supplements/6.106_least_significant_1.png" alt="" style="width:300px; margin-top: 10px"/></center>
		- Both `x` and `-x` end up having the same least significant 1
- Is `x` a power of 2 (i.e. only has a single 1)?
	- `(x != 0) && (x == x & (-x))`
		- Special case for `x=0`
		- Otherwise, we use 2's complement logic; `x & (-x)` returns just the least significant 1 of `x`.
				<center><img src="School Supplements/6.106_is_power_of_2.png" alt="" style="width:550px; margin-top: 10px"/></center>
	- Alternative: `(x & (x-1)) == 0`

- Swapping 2 variables
	- `x = x ^ y`
	- `y = x ^ y`
	- `x = x ^ y`
	- Why this works: `XOR` is its own inverse: `(x ^ y) ^ y = x`
	- HOWEVER: bad for instruction-level parallelism; must happen serially
	- Using a temporary variable is actually faster
- Min of 2 ints
	- Simple method: `r = (x < y) ? x : y`
	- `r = y ^ ((x ^ y) & -(x < y))`
		- `(x < y)` returns all 1 if `x < y`, else 0. Then, the minus sign turns this into all 1's (an all-1 mask) or all 0's.
		- if `x < y`:
			- `r = y ^ (x ^ y) = x`
		- if `x > y`:
			- `r = y ^ ((x ^ y) & 0) = y`
		- Good if branch is unpredictable, you want to avoid branching
	- NOTE: in practice, `r = a ? x : y` are optimized by compiler to use `cmov` instruction, so are actually very fast
- Modular Addition
	- `r = (x + y) % n`, where `0 <= x < n`, `0 <= y < n`
	- Want to avoid branching, and want to avoid division
		- `z = x + y`
		- `r = z - (n & -(z >= n))`
			- If `z >= n`, then `r = z - n`. If `z < n`, then `r = z`.
- Modulo powers of 2
	- `r = x % n` where `n` is a power of 2
	- `r = x & (n-1)` is equivalent
- Population Count
	- Count number of 1's in `x`
	- Simple:
		- `for (r=0; x!=0; ++r)`
			- `x &= x - 1`

## Review
- Intuition of subtracting 1:
	- `10110000` --> `10101111`
	- essentially remove the last 1, then replace all the trailing 0's with 1's
- 2's complement:
	- Leading 1 is negative valued; all other digits positive valued
	- To find 2's complement representation, this is a simple trick: `-x = ~x + 1`
		1. Represent `+x` in binary
		2. Flip all the bits
		3. Add 1
	- i.e.: to represent -28:
		- +28 in binary: `00011100`
		- ~28: `11100011`
		- ~28 + 1: `11100100`   <--   -28 in binary
- Speculative branch prediction
	- Keeps history of running this branch in the past -- repeats most common from history
	- Note: branch mis-prediction is costly -- on order of an L2 cache miss
