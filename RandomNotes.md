# Transformer-based Model Predictive Control: Trajectory Optimization via Sequence Modeling
##### General Knowledge about Transformers/Autoregressive Inference
- Token sequence is built up autoregressively -- i.e. it may start at size $m$, containing just prefix tokens (inputs to the model). At each autoregressive input, it appends new tokens.
- Transformer inputs tensor $(L, d_{\text{model}})$, where $L$ is length of token sequence and $d_{\text{model}}$ is dimension of token. $L$ just needs ot be less than some max context length.
---
##### Definitions
- Subscript notation: $\{\}_i = \{\}(t_i)$
- $\mathbf{x}_i$, $\mathbf{u}_i$: states and controls at timestep $i$
- $r_i = -J(\mathbf{x}_i, \mathbf{u}_i)$: reward at timestep $i$
- $\tau = (\mathbf{x}_i, \mathbf{u}_i, r_i ~ \forall i)$: trajectory
- $\tau = (\mathcal{T}_i, \mathcal{R}_i, \mathcal{C}_i, \mathbf{x}_i, \mathbf{u}_i, r_i ~ \forall i)$: model's trajectory representation
- $\mathcal{T}_i$: target state for timestep $i$
- $\mathcal{R}_i$: reward budget for timesteps $i+$
    - Set by expert during training
    - $R_1$ set to lowest possible upper bound on reward;
    - $R_{i>1}$ generated by model
- $\mathcal{C}_i$: constraint violation budget for timesteps $i+$
    - Set by expert during training
    - $C_1$ set to 0 during inference to demand a feasible trajectory
    - $C_{i>1}$ generated by model
- $\sigma_0 = (\mathcal{T}_1, \mathcal{R}_1, \mathcal{C}_1, \mathbf{x}_1)$: user-provided initial conditions

Cost function (9c is an obstacle constraint):
$$
\begin{align}
\min_{\mathbf{x}_i, \mathbf{u}_i} & \quad \sum_{i=1}^{N} \| \mathbf{u}_i \|_p^q \tag{9a} \\\text{subject to} & \quad \mathbf{x}_{i+1} = \hat{f}(\mathbf{x}_i, \mathbf{u}_i) \quad \forall i \in [1, N], \tag{9b} \\& \quad \Gamma(\mathbf{x}_i) \geq 0 \quad \forall i \in [1, N], \tag{9c} \\& \quad \mathbf{x}_1 = \mathbf{x}_{\text{start}}, \quad \mathbf{x}_{N+1} = \mathbf{x}_{\text{goal}}. \tag{9d}
\end{align}
$$
---
##### Training- $N$: number of timesteps
- $N_D$: number of samples in dataset
- $H$: MPC horizon

Standard GPT transformer model.
Training loss (L2 norm between predicted and expert):
$$\mathcal{L}(\tau) = \sum_{n=1}^{N_D} \sum_{i=1}^{N} \left( \|\mathbf{x}_i^{(n)} - \hat{\mathbf{x}}_i^{(n)}\|_2^2 + \|\mathbf{u}_i^{(n)} - \hat{\mathbf{u}}_i^{(n)}\|_2^2 \right),$$
where (i.e. the states at timestep $i$ are conditioned on the trajectory up to timestep $i-1$):
$$\hat{\mathbf{x}}_i^{(n)} \sim p_\theta(\mathbf{x}_i^{(n)} \mid \tau_{<t_i}^{(n)})$$
$$\hat{\mathbf{u}}_i^{(n)} \sim p_\theta(\mathbf{u}_i^{(n)} \mid \tau_{<t_i}^{(n)}, \mathbf{x}_i^{(n)})$$
---
##### Inference
- Given $\sigma_0=(\mathcal{T}_1, \mathcal{R}_1, \mathcal{C}_1, \mathbf{x}_1)$, model generates $\mathbf{u}_1$, uses dynamics model to generate $\mathbf{x}_2$, then evaluates/updates $\mathcal{R}_2$ and $\mathcal{C}_2$. $\mathcal{T}_2$ is either copied from $\mathcal{T}_1$ or set to something new if tracking a moving target state.
---
##### Long Horizon Guidance- Transformer trained on "full-horizon" ($N$) trajectories
- Inference only evaluated up to short-horizon ($H$) timesteps
---
##### Fine-tuning
- Why: running a policy trained by experts offline and open-loop in a closed-loop system is unstable:
    - Firstly, offline policy is trained on a different (full) horizon, thus finds different trajectories. The full-horizon trajectories will tend to visit different state-space regions compared to short-horizon trajectories.
    - Secondly, offline policy is trained only on experts, stays precisely on expert manifold. Meanwhile, executing the learner + warm-started MPC optimizer closed-loop deviates from expert manifold -- model doesn't perform well off the expert manifold.
    - Thus, fine-tuning is needed so the model learns optimal trajectories even off the expert-manifold.
- Implementation:
    - Based on DAGGER: simulate (using simulated dynamics) the closed-loop behavior; at each time-step, run MPC + query the expert to generate a new ground truth trajectory. Add this trajectory to the dataset. Then roll forward dynamics and repeat
    - Alternate between rolling forward dynamics using expert trajectory's suggested controls and using optimized controls from current model's trajectory (using as warm-start)
    - Run MPC on many different horizon lengths ($H$) so the model learns the closed-loop behavior for a variety of horizon lengths

## Inverse Dynamics Control
(aka "Computed-torque Control")
- Dynamics of a fully-actuated manipulator:
	<center><img src="ReadingNotesSupplements/inverse_dynamics.png" alt="" style="width:25%; margin-top: 10px"/></center>
	- $u$ are joint torques (aka "generalized forces")
- Inverse dynamics control sets:
	- 	<center><img src="ReadingNotesSupplements/inverse_dynamics_control.png" alt="" style="width:25%; margin-top: 10px"/></center>
	- Plugging this into the manipulator dynamics, we get:
			$$ M(q) \ddot{q} + C(q, \dot{q}) \dot{q} = \tau_g(q) + M(q) \ddot{q}_d + C(q, \dot{q})\dot{q} - \tau_g(q)  \quad \implies \quad M(q) \ddot{q} = M(q)\ddot{q}_d $$
		- Achieving the desired acceleration
- Usually, to follow a trajectory, we don't just differentiate the trajectory $q_0(t)$ twice to get an acceleration trajectory to command to the inverse dynamics controller; we also want some feedback on position/velocity.
	- We therefore choose $\ddot{q}_d$ so the error $(q - q_0)$ between actual robot positions and trajectory planned positions and behaves like a stable 2nd-order system (and therefore converges to 0):
		$$\ddot{q}_0 - \ddot{q}_d + K_p(q - q_0) + K_d(\dot{q} - \dot{q}_0) = 0$$
	- In particular, define $\ddot{q}_d$:
		$$ \ddot{q}_d = \ddot{q}_0 + K_p(q - q_0) + K_d(\dot{q} - \dot{q}_0) = 0 $$
		- Note that as position error and velocity error $(q - q_0)$, $(\dot{q} - \dot{q}_0)$ go to zero, $\ddot{q}_d$ converges to the trajectory's planned acceleration $\ddot{q}_0$
	- We feed our computed $\ddot{q}_d$ to our inverse dynamics control law $u = M(q) \ddot{q}_d + C(q, \dot{q}) \dot{q} - \tau_g (q)$
- Note: even for primitive trajectories (i.e. piece-wise, waypoint trajectories with piecewise zero-order hold velocities)
#### An Aside: Operational Space Control (OSC)
- Basically identical to Inverse Dynamics Control, but you essentially multiply the entire inverse dynamics equation by the task-space Jacobian and use task-space Mass/Coriolis matrices (and you multiply the resulting task-space force by the inverse Jacobian to convert to joint-space torques).

## Differential IK

Broad idea: use Geometric Jacobian map desired spatial velocity to joint velocities for robot to execute
$$V_{spatial} = J \dot{q}$$
In practice, (combined with a lower-level controller, i.e. Inverse Dynamics Controller) used to convert end-effector state commands to motor torques.

Drake [`DifferentialInverseKinematicsIntegrator`]([Drake: DifferentialInverseKinematicsIntegrator Class Reference](https://drake.mit.edu/doxygen_cxx/classdrake_1_1multibody_1_1_differential_inverse_kinematics_integrator.html)) implements the Diff IK pipeline. Effectively:
```python
while simulation_running: 
	# 1. Get current state 
	q_current = robot.get_positions()
	X_current = ForwardKinematics(q_current)
	
	# 2. Compute Spatial Velocity from Error (P-control) 
	V_spatial = Gain * (X_goal - X_current)
	
	# 3. Solve DiffIK (as a QP)
	v_joint = Solve(J * v = V_spatial) 
	
	# 4. Integrate to get position command
	q_command = q_current + v_joint * dt
	
	# 5. Clamp to joint limits
	q_command = clamp(q_command)
	
	robot.set_command(q_command)
```

A common DiffIK formulation is as a QP (automatically clamps joint positions and velocities within limits):
<center><img src="ReadingNotesSupplements/diff_ik_qp.png" alt="" style="width:30%; margin-top: 10px"/></center>

Then, `InverseDynamicsController` takes `q_command` and converts to motor torques. 
- Note: the `InverseDynamicsController` will also want a desired $\dot{q}$ command
- Therefore, it's often paired with [`StateInterpolatorWithDiscreteDerivative`](https://drake.mit.edu/doxygen_cxx/classdrake_1_1systems_1_1_state_interpolator_with_discrete_derivative.html) to compute desired $\dot{q}$ numerically ($\frac{q_t - q_{t-1}}{dt}$), using the final (clamped) `q_command`.

Note: generally, we do not calculate a feedforward acceleration. This is because, at each replan, Diff IK generates a constant velocity command; thus the desired acceleration will look like a series of dirac delta spikes. 

Diff IK usually sufficient for "slow" manipulation... for faster, more accurate control (i.e. BD's Atlas), use a whole-body controller or MPC (both solve optimization-problems to determine desired configuration states, but whole-body control has a horizon of 1).


## PID
There is a key distinction btwn PID w/ moving vs stationary setpoint:
- Classic PID:
	- Any non-zero velocity is penalized; you want the system to be stationary
		$$ u = k_p(x - x_d) + k_d(\frac{d}{dt}(x-x_d)) + k_i \int (x - x_d) $$
- Moving Setpoint PID (i.e. to track a trajectory with position and velocity setpoints):
	- Relative velocity (compared to desired velocity) is penalized
		$$ u = k_p(x - x_d) + k_d(\dot{x} - v_d) + k_i \int (x - x_d) $$

## Fourier Transform

Credits: [https://www.youtube.com/watch?v=spUNpyF58BY]

Purpose: Broadly, decomposes a wave function into a combination of sine waves. Technically, it takes an arbitrary wave function $g(t)$ and transforms it into a new function $\hat{g}(f)$ that contains spikes at the generating sine wave frequencies.

The new function $\hat{g}(f)$ takes frequency as an input (and outputs an complex number that is the "intensity" at each frequency):

$$ \hat{g}(f) =\int_{t_1}^{t_2} g(t) e^{-2 \pi i ft} dt $$

Intuitively, this is what the function is doing:
- First, it takes $e^{-2 \pi i ft}$, which corresponds to some point on the unit circle in the complex plane. Recall that $e^{it}$ = $\text{cos}(t) + i ~\text{sin}(t)$, so increasing $t$ from $0$ to $2\pi$ is like walking around the edge of a unit circle. Then, the input $f$ controls the rate we travel around the unit circle.
- Multiplying $e^{-2 \pi i ft}$ by $g(t)$ effectively applies $g(t)$ onto that unit circle; it's like wrapping the wave function on the circle.
- Taking the integral is effectively taking the "average" of all the points in the complex plane (the red dot in the bottom left graph). "Average" in quotations because it is more of a sum than an average (it's not divided by $(t_2 - t_1)$), but this just has the effect of scaling $\hat{g}(f)$ up for longer wave signals.
- Taking the real part of the output (i.e. the x-coordinate of the red dot), we find that it spikes around the frequencies of the sine waves constructing $g(t)$ (see the spikes on the top right graph).
